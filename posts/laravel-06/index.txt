<h2>2. Pest</h2>
<p><strong>Pest</strong>는 PHPUnit 위에서 <code>it(&#39;...&#39;)</code> 문법으로 테스트를 쓰는 도구다. 러너는 PHPUnit이고, 단언(assert)도 같다. Laravel 신규 프로젝트에서 Pest를 기본으로 고르는 팀이 많다. PHPUnit 클래스 스타일과 섞어도 동작한다. 팀에서 하나만 정하면 된다.</p>

<h2>4. DB와 Factory</h2>
<pre><code class="hljs language-php"><span class="hljs-title function_ invoke__">uses</span>(<span class="hljs-title class_">RefreshDatabase</span>::<span class="hljs-variable language_">class</span>);</code></pre>
<p><strong>RefreshDatabase</strong>는 테스트마다 마이그레이션으로 DB를 깨끗한 상태로 돌린다. 테스트가 서로를 더럽히지 않게 하는 기본값이다. 느리면 <code>DatabaseTransactions</code>나 <code>php artisan test --parallel</code>을 검토한다.</p>
<p>데이터는 Factory로 만든다. 테스트 안에 <code>User::create([&#39;email&#39; =&gt; &#39;a@b.com&#39;, ...])</code>를 나열하면 컬럼이 늘 때마다 전부 고친다. 3편의 <code>published()</code> state가 여기 쓰인다.</p>
<p>운영 DB를 테스트가 건드리면 안 된다. <code>phpunit.xml</code>의 <code>APP_ENV=testing</code>과 별도 SQLite/테스트 DB를 확인한다.</p>

<hr>
<h2>7. 인가는 네 줄이면 회귀를 막는다</h2>
<p>한 리소스에 아래만 있어도 보안 구멍이 다시 열리기 어렵다.</p>
<ul>
<li>guest → 401</li>
<li>다른 사용자 → 403</li>
<li>소유자 → 200</li>
<li>관리자 → 200 (역할이 있다면)</li>
</ul>
<p>미들웨어 <code>auth</code>만 있고 Policy 테스트가 없으면, 인증된 아무나 통과하는 코드를 머지해도 초록불이 유지된다.</p>
<hr>
<h2>8. 테스트 환경</h2>
<p><code>phpunit.xml</code> 또는 <code>Pest.php</code>에서:</p>
<ul>
<li><code>APP_ENV=testing</code></li>
<li>SQLite <code>:memory:</code> 또는 전용 DB</li>
<li><code>MAIL_MAILER=array</code></li>
<li><code>QUEUE_CONNECTION=sync</code> (또는 테스트에서 fake)</li>
</ul>
<p><code>.env.testing</code>을 두는 팀도 있다. 로컬 <code>.env</code>의 Redis·실메일 설정이 테스트에 새어 들면 안 된다.</p>
<hr>
<h2>9. 흔한 실수</h2>
<ul>
<li>private 메서드를 리플렉션으로 테스트한다. 공개 행동만 본다.</li>
<li>한 <code>it</code>에 생성·수정·삭제·권한을 다 넣는다. 실패 지점이 안 보인다.</li>
<li><code>sleep</code>이나 실제 시계에 의존한다.</li>
<li>Factory 없이 하드코딩 insert를 반복한다.</li>
<li>외부 결제 URL을 테스트가 호출한다.</li>
</ul>
<hr>
<h2>연습</h2>
<ol>
<li>게시글 생성 성공(201)과 검증 실패(422) Feature 테스트를 작성한다.</li>
<li>타인 수정 403을 고정한다.</li>
<li><code>Http::fake</code>로 결제 클라이언트를 고립한다.</li>
<li><code>Queue::fake</code>로 환영 메일 Job이 쌓이는지 확인한다.</li>
</ol>
