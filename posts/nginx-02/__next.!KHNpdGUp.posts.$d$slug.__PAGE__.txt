3:T201d,<h1>Nginx에서 HTTPS·TLS 종단하기</h1>
<blockquote>
<p>요약: 인증서를 Nginx에 두고 443에서 TLS를 끝낸 뒤, 80 요청을 HTTPS로 보내고 앱에는 암호화가 끝났다는 헤더를 넘긴다.</p>
</blockquote>
<hr>
<h2>언제 앞단에서 TLS를 끊는가</h2>
<p>브라우저와 서버 사이 트래픽을 암호화할 때 TLS(전송 계층 보안)를 쓴다. HTTPS는 HTTP에 TLS를 얹은 것이다.</p>
<p>인증서를 앱마다 넣지 않고 Nginx(또는 로드밸런서)에서 끝낸다. 앱은 내부 HTTP만 받으면 된다. 인증서 갱신·프로토콜 버전·보안 헤더를 한곳에서 바꾼다.</p>
<p>클라우드에서 로드밸런서가 이미 TLS를 끝내면 Nginx는 HTTP만 받아도 된다. 이 글은 Nginx가 인증서를 직접 들고 있는 경우이다.</p>
<hr>
<h2>443에서 인증서를 연다</h2>
<p>Let’s Encrypt를 썼다면 경로가 아래와 같다. 상용 인증서도 <code>fullchain</code>과 비밀키 두 파일이라는 점은 같다.</p>
<pre><code class="hljs language-nginx"><span class="hljs-section">server</span> {
    <span class="hljs-attribute">listen</span> <span class="hljs-number">443</span> ssl;
    <span class="hljs-attribute">http2</span> <span class="hljs-literal">on</span>;
    <span class="hljs-attribute">server_name</span> example.com;

    <span class="hljs-attribute">ssl_certificate</span>     /etc/letsencrypt/live/example.com/fullchain.pem;
    <span class="hljs-attribute">ssl_certificate_key</span> /etc/letsencrypt/live/example.com/privkey.pem;

    <span class="hljs-attribute">ssl_protocols</span> TLSv1.<span class="hljs-number">2</span> TLSv1.<span class="hljs-number">3</span>;

    <span class="hljs-section">location</span> / {
        <span class="hljs-attribute">proxy_pass</span> http://127.0.0.1:3000;
        <span class="hljs-attribute">proxy_set_header</span> Host <span class="hljs-variable">$host</span>;
        <span class="hljs-attribute">proxy_set_header</span> X-Forwarded-Proto https;
        <span class="hljs-attribute">proxy_set_header</span> X-Forwarded-For <span class="hljs-variable">$proxy_add_x_forwarded_for</span>;
    }
}</code></pre>
<p><code>ssl_certificate</code>는 사이트 인증서와 중간 인증서가 이어진 체인이다. 리프만 넣으면 일부 브라우저가 체인을 못 잇는다. <code>privkey</code>는 비밀키이다. 권한이 넓으면 키 유출과 같다.</p>
<p><code>X-Forwarded-Proto</code>를 <code>https</code>로 고정한다. 빠지거나 <code>http</code>로 남으면 앱이 <code>http://</code> 링크를 만들고, Secure 쿠키를 안 붙인다. 리다이렉트 루프가 나기도 한다.</p>
<p>구버전 Nginx는 <code>listen 443 ssl http2;</code> 한 줄이다. 새 버전은 <code>listen 443 ssl;</code>과 <code>http2 on;</code>을 분리한다. <code>nginx -V</code>로 문법을 확인한다.</p>
<hr>
<h2>80은 443으로만 보낸다</h2>
<p>암호화되지 않은 80은 같은 경로를 HTTPS로 돌린다. <code>return 301</code>이 가장 짧다.</p>
<pre><code class="hljs language-nginx"><span class="hljs-section">server</span> {
    <span class="hljs-attribute">listen</span> <span class="hljs-number">80</span>;
    <span class="hljs-attribute">server_name</span> example.com;
    <span class="hljs-attribute">return</span> <span class="hljs-number">301</span> https://<span class="hljs-variable">$host</span><span class="hljs-variable">$request_uri</span>;
}</code></pre>
<p><code>$host$request_uri</code>는 호스트와 경로·쿼리를 유지한다. <code>https://example.com/</code>처럼 루트만 박으면 북마크 경로가 날아간다.</p>
<p>인증서 발급이 HTTP-01(ACME, 자동 인증서 관리 환경의 HTTP 검증)이면 <code>/.well-known/acme-challenge/</code>는 리다이렉트하면 안 된다. 검증 파일은 평문으로 열려 있어야 한다.</p>
<pre><code class="hljs language-nginx"><span class="hljs-section">server</span> {
    <span class="hljs-attribute">listen</span> <span class="hljs-number">80</span>;
    <span class="hljs-attribute">server_name</span> example.com;

    <span class="hljs-section">location</span> /.well-known/acme-challenge/ {
        <span class="hljs-attribute">root</span> /var/www/certbot;
    }

    <span class="hljs-section">location</span> / {
        <span class="hljs-attribute">return</span> <span class="hljs-number">301</span> https://<span class="hljs-variable">$host</span><span class="hljs-variable">$request_uri</span>;
    }
}</code></pre>
<p>발급이 끝난 뒤에도 이 location을 남겨 두면 갱신이 같은 경로로 통과한다.</p>
<hr>
<h2>갱신과 HSTS</h2>
<table>
<thead>
<tr>
<th>항목</th>
<th>하는 일</th>
</tr>
</thead>
<tbody><tr>
<td>갱신</td>
<td><code>certbot renew</code>가 성공한 뒤 deploy hook에서 <code>nginx -t &amp;&amp; systemctl reload nginx</code></td>
</tr>
<tr>
<td>프로토콜</td>
<td>TLS 1.2와 1.3만 연다. 1.0·1.1은 끈다</td>
</tr>
<tr>
<td>HSTS</td>
<td>안정적으로 HTTPS만 열린 뒤에 <code>Strict-Transport-Security</code>를 넣는다</td>
</tr>
<tr>
<td>키 권한</td>
<td><code>privkey.pem</code>은 root(또는 nginx 사용자)만 읽게 둔다</td>
</tr>
</tbody></table>
<p>HSTS(HTTP 엄격 전송 보안)는 브라우저에게 “이 사이트는 앞으로 HTTPS만”이라고 기억하는 헤더이다. 한 번 나가면 HTTP로 되돌리기 어렵다. 인증서 오류가 남은 상태에서는 넣지 않는다.</p>
<pre><code class="hljs language-nginx"><span class="hljs-attribute">add_header</span> Strict-Transport-Security <span class="hljs-string">&quot;max-age=31536000; includeSubDomains&quot;</span> always;</code></pre>
<p><code>max-age</code>는 초 단위이다. 먼저 짧은 값으로 시험한 뒤 1년으로 늘린다. 서브도메인이 HTTP만 있으면 <code>includeSubDomains</code>를 빼다.</p>
<p>www와 apex(루트 도메인) 중 하나만 정규 URL로 정한다. 인증서는 둘 다 커버하거나, 한쪽에서 다른 쪽으로 301한다. 정책이 섞이면 쿠키와 SEO(검색 엔진 최적화)가 갈린다.</p>
<p>인증서가 브라우저에 실제로 쓰이는지 확인한다.</p>
<pre><code class="hljs language-bash"><span class="hljs-built_in">sudo</span> nginx -t
<span class="hljs-built_in">sudo</span> systemctl reload nginx
curl -I http://example.com/
curl -IIv --http1.1 https://example.com/</code></pre>
<p>80 응답은 <code>301</code>과 <code>Location: https://...</code>이어야 한다. 443은 인증서 주체(CN/SAN)가 요청 호스트와 같아야 한다. 불일치면 <code>server_name</code>과 인증서 발급 이름을 맞춘다.</p>
<hr>
<h2>흔한 실수</h2>
<ul>
<li><code>fullchain</code> 대신 <code>cert.pem</code>만 넣는다. 모바일에서 체인 오류가 난다.</li>
<li><code>X-Forwarded-Proto</code>를 <code>$scheme</code>으로 두었는데 내부가 HTTP라서 앱이 계속 <code>http</code>를 본다. 443 블록에서는 <code>https</code>로 명시한다.</li>
<li>80 전체를 301하면서 ACME 경로까지 막는다. 갱신이 실패한다.</li>
<li>HSTS를 인증서 만료 직전 사이트에 바로 켠다. 만료 동안 브라우저가 HTTP 폴백을 거부한다.</li>
<li>reload만 하고 인증서 파일을 안 읽게 한다. 심볼릭 링크가 바뀌었으면 프로세스 사용자 권한으로 새 파일을 읽을 수 있는지 본다.</li>
</ul>
<hr>
<h2>정리</h2>
<p>HTTPS는 인증서 경로 두 줄을 넣는 일이 아니다. 443에서 TLS를 끝내고, 80을 안전하게 돌리고, 앱에는 <code>https</code>로 끝났다고 알리고, 갱신 후 reload가 자동이어야 한 세트가 된다.</p>
<hr>
<h2>연습</h2>
<ol>
<li>스테이징 도메인에 위 80/443 블록을 넣고 <code>curl -I http://도메인</code>이 301로 <code>https://</code>를 가리키는지 확인한다.</li>
<li>앱이 그리는 로그인 링크가 <code>https://</code>인지 보고, <code>X-Forwarded-Proto</code>를 빼면 스킴이 어떻게 바뀌는지 비교한다.</li>
<li>인증서 만료일을 <code>openssl x509 -in fullchain.pem -noout -enddate</code>로 확인하고, renew hook에 <code>nginx -t</code>와 reload가 있는지 본다.</li>
</ol>
