23:T5e8f,<h1>InfluxDB: 시계열 데이터베이스의 개념과 실무 활용</h1>
<blockquote>
<p>요약: IoT 센서 데이터, 서버 모니터링 메트릭, 실시간 로그 수집에 특화된 Time-Series DB인 InfluxDB의 데이터 모델(Line Protocol, Tag vs Field)과 쿼리, Spring Boot 연동을 다룬다.</p>
</blockquote>
<hr>
<h2>1. 시계열 데이터(Time-Series Data)와 TSDB란?</h2>
<p><strong>시계열 데이터(Time-Series Data)</strong> 는 <strong>시간의 흐름에 따라 순차적으로 기록되는 데이터 포인트의 연속</strong>을 의미한다.</p>
<ul>
<li><strong>대표적인 예시</strong>:<ul>
<li>서버 및 인프라 메트릭: CPU 사용률, 메모리 점유율, 초당 네트워크 I/O</li>
<li>IoT / 스마트 팩토리: 공장 설비 온도, 센서 진동값, 전력 소비량, 전기차 배터리 잔량</li>
<li>금융 / 핀테크: 초/밀리초 단위 주식 호가 및 거래량</li>
<li>애플리케이션 로그 / 이벤트: 초당 API 요청 수, 응답 레이턴시</li>
</ul>
</li>
</ul>
<h3>왜 RDB(MySQL, PostgreSQL)로 시계열 데이터를 처리하기 어려울까?</h3>
<p>일반 RDB는 레코드의 빈번한 <strong>수정(UPDATE)</strong> 과 복잡한 <strong>테이블 간 조인(JOIN)</strong> 에 최적화되어 있다. 하지만 시계열 데이터는 다음과 같은 극단적인 특징을 갖는다:</p>
<ol>
<li><strong>압도적인 쓰기(Write-Heavy) 트래픽</strong>: 초당 수만~수십만 건의 센서/메트릭 데이터가 끊임없이 쏟아진다.</li>
<li><strong>수정(UPDATE)과 삭제(DELETE)가 거의 없음</strong>: 과거의 센서 기록은 한 번 기록되면 수정되지 않는 불변(Append-Only) 데이터다.</li>
<li><strong>시간 범위 기반의 집계(Aggregation) 쿼리 중심</strong>: 개별 레코드 1건을 조회하기보다 &quot;최근 1시간 동안의 5분 단위 평균 온도&quot;, &quot;최근 24시간 동안의 95백분위 레이턴시&quot; 등을 조회한다.</li>
<li><strong>수명 주기(Data Retention) 관리 필요</strong>: 1년 전의 초 단위 상세 메트릭은 필요 없고 일 단위 평균만 남기거나 일정 기간 후 자동 삭제되어야 한다.</li>
</ol>
<p>이러한 시계열 데이터 처리에 특화된 오픈소스 데이터베이스가 바로 <strong>TSDB(Time Series Database)</strong> 이며, 그중 가장 널리 쓰이는 대표주자가 <strong>InfluxDB</strong>다.</p>
<hr>

<h3>⚠️ 실무 치명적 실수: Tag vs Field 구분 기준 (Series Cardinality)</h3>
<ul>
<li><strong>Tag로 넣어야 할 것</strong>: 값의 가짓수가 제한적이고 검색/필터링 조건으로 자주 쓰이는 것 (서버 호스트명, 리전명, 디바이스 ID, 고객 ID 등)</li>
<li><strong>Field로 넣어야 할 것</strong>: 연속적으로 계속 변하는 실제 측정값 (온도, 전압, CPU%, 메모리 바이트)이나 <strong>유니크한 값이 무한히 생성되는 값(UUID, 요청마다 다른 고유 트랜잭션 ID 등)</strong></li>
</ul>
<blockquote>
<p><strong>주의 (High Cardinality 폭탄)</strong>: 고유한 값이 무한히 생성되는 UUID나 나노초 단위의 랜덤 문자열을 Tag로 지정하면, InfluxDB가 내부적으로 생성하는 시계열 인덱스(Series)가 기하급수적으로 폭증하여 <strong>메모리(RAM) 부족으로 서버가 다운(OOM)</strong> 된다.</p>
</blockquote>
<hr>
<h2>3. 라인 프로토콜 (Line Protocol) — InfluxDB 전용 데이터 포맷</h2>
<p>InfluxDB에 데이터를 입력(Ingest)할 때는 JSON 대신 초경량 텍스트 포맷인 <strong>Line Protocol</strong>을 사용한다. JSON 파싱 오버헤드가 없어 초당 수십만 건을 가볍게 밀어 넣을 수 있다.</p>
<pre><code class="hljs language-text">&lt;measurement&gt;[,&lt;tag_key&gt;=&lt;tag_value&gt;...] &lt;field_key&gt;=&lt;field_value&gt;[,&lt;field_key&gt;=&lt;field_value&gt;...] [timestamp]</code></pre>
<h3>작성 예시</h3>
<pre><code class="hljs language-text"># 쉼표(,)와 공백( )의 위치가 매우 중요함
cpu_metrics,host=web-server-01,region=ap-northeast-2 usage_user=24.5,usage_system=5.2,idle=70.3 1724835600000000000

factory_sensor,factory_id=f01,line=A,sensor_id=temp_04 temperature=36.8,humidity=55.2 1724835601000000000</code></pre>
<ol>
<li><code>cpu_metrics</code>: Measurement 이름</li>
<li><code>,host=web-server-01,region=ap-northeast-2</code>: 쉼표로 연결된 Tag 세트 (인덱싱 대상)</li>
<li><code> </code> (공백 1칸): Tag와 Field를 구분하는 필수 구분자</li>
<li><code>usage_user=24.5,usage_system=5.2</code>: 쉼표로 연결된 Field 세트 (측정값)</li>
<li><code> </code> (공백 1칸): Field와 타임스탬프를 구분하는 필수 구분자</li>
<li><code>1724835600000000000</code>: 나노초 단위 Unix Timestamp (생략 시 InfluxDB 서버 수신 시각으로 자동 기록)</li>
</ol>

<h2>4. 데이터 쿼리하기 (Flux &amp; InfluxQL)</h2>
<p>InfluxDB는 버전에 따라 2가지 쿼리 언어를 지원한다.</p>
<ul>
<li><strong>InfluxQL</strong>: SQL과 유사한 전통적인 문법 (InfluxDB 1.x / 3.x 지원)</li>
<li><strong>Flux</strong>: 함수형 파이프라인(<code>|&gt;</code>) 기반의 고기능 쿼리 스크립트 언어 (InfluxDB 2.x 중심)</li>
</ul>

<span class="hljs-keyword">GROUP</span> <span class="hljs-keyword">BY</span> <span class="hljs-type">time</span>(<span class="hljs-number">5</span>m) fill(linear);</code></pre>

<h2>6. 데이터 보관 주기(Retention Policy)와 다운샘플링(Downsampling)</h2>
<p>시계열 데이터는 시간이 지날수록 데이터량이 천문학적으로 불어난다. 이를 효율적으로 관리하기 위해 2가지 전략을 반드시 설정해야 한다.</p>
<h3>1) 보관 주기 (Retention Policy / TTL)</h3>
<p>Bucket 생성 시 데이터의 자동 폐기 시한을 지정한다.</p>
<ul>
<li>예: <code>raw-metrics</code> 버킷은 7일 후 자동 삭제 (<code>retention: 7d</code>)</li>
</ul>
<h3>2) 다운샘플링 (Downsampling Task)</h3>
<p>7일이 지나 초 단위 원본 데이터는 삭제되더라도, 1년 뒤 통계를 위해 <strong>&quot;1시간 단위 평균값&quot;</strong> 은 장기 보관하고 싶을 때 사용한다.</p>
<p>InfluxDB의 <strong>Task(스케줄러)</strong> 기능을 이용해 백그라운드에서 주기적으로 원본 데이터를 집계하여 장기 보관용 버킷(<code>long-term-metrics</code>, retention: 1년)으로 복사해 둔다.</p>
<pre><code class="hljs language-flux">// <span class="hljs-number">1</span>시간마다 실행되어 <span class="hljs-number">1</span>시간 평균을 장기 보관 버킷으로 전송하는 Task
option task = {name: <span class="hljs-string">&quot;downsample_hourly_temp&quot;</span>, every: <span class="hljs-number">1h</span>}

from<span class="hljs-punctuation">(</span>bucket: <span class="hljs-string">&quot;sensor-data&quot;</span><span class="hljs-punctuation">)</span>
  |&gt; range<span class="hljs-punctuation">(</span>start: -task.every<span class="hljs-punctuation">)</span>

<h2>8. 실무 체크리스트</h2>
<ul>
<li><input disabled="" type="checkbox"> <strong>Tag 카디널리티 검증</strong>: UUID나 무작위 문자열처럼 무한히 증가하는 값을 Tag로 지정하지 않았는가?</li>
<li><input disabled="" type="checkbox"> <strong>라인 프로토콜 공백 체크</strong>: 태그와 필드 사이, 필드와 타임스탬프 사이의 공백 구분을 정확히 지켰는가?</li>
<li><input disabled="" type="checkbox"> <strong>배치 쓰기(Batch Write) 활용</strong>: 단건 쿼리 호출 대신 버퍼를 둔 비동기 배치 쓰기로 네트워크 I/O를 절약하고 있는가?</li>
<li><input disabled="" type="checkbox"> <strong>Retention Policy 설정</strong>: 버킷 생성 시 무기한 보관 대신 도메인에 맞는 적절한 보관 주기(7일, 30일 등)를 지정했는가?</li>
