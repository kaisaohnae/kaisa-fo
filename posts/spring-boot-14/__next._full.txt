24:T7a60,<h1>Gradle 빌드와 멀티모듈 아키텍처 설계</h1>
<blockquote>
<p>요약: Gradle 빌드 생명주기, Kotlin DSL(build.gradle.kts), 의존성 스코프 차이(implementation vs api), 플러그인 작성, 멀티모듈 프로젝트 설계 패턴(계층형, MSA/공통 도메인형, 헥사고날)을 다룬다.</p>
</blockquote>
<hr>
<h2>1. Gradle이란 무엇이며 왜 Maven보다 많이 쓰일까?</h2>
<p><strong>Gradle</strong>은 현대 JVM 생태계에서 가장 널리 사용되는 빌드 자동화 도구(Build Automation Tool)다. 소스 코드를 컴파일하고, 테스트를 실행하며, 의존성을 다운로드하고, 최종적으로 배포 가능한 실행 파일(Jar, War)을 패키징하는 전 과정을 관리한다.</p>
<h3>Maven vs Gradle 핵심 비교</h3>
<table>
<thead>
<tr>
<th>비교 항목</th>
<th>Apache Maven</th>
<th>Gradle</th>
</tr>
</thead>

<td><strong>설정 언어</strong></td>
<td>XML (<code>pom.xml</code>) — 정적이고 장황함</td>
<td>Kotlin DSL (<code>build.gradle.kts</code>) 또는 Groovy — 동적이며 간결함</td>
</tr>

</tr>
<tr>

<td>의존성 그래프 기반, 서브모듈별 자유로운 설정 및 플러그인 주입 가능</td>

</tr>

<p>Spring Boot 3.x부터는 공식 문서 및 스타터(start.spring.io)에서 <strong>Gradle + Kotlin DSL</strong>을 기본 권장선으로 채택하고 있다.</p>
<hr>
<h2>2. Gradle의 3단계 빌드 생명주기 (Build Lifecycle)</h2>
<p>Gradle의 빌드가 실행될 때 내부적으로는 항상 다음 <strong>3단계(Initialization ➔ Configuration ➔ Execution)</strong> 를 거친다. 이 생명주기를 이해하지 못하면 빌드 스크립트 작성 시 실행 순서가 꼬이는 실수를 하게 된다.</p>
<pre><code class="hljs">┌─────────────────────────────────────────────────────────────┐
│ <span class="hljs-number">1</span>. Initialization <span class="hljs-punctuation">(</span>초기화 단계<span class="hljs-punctuation">)</span>                               │
│   - settings.gradle<span class="hljs-punctuation">(</span>.kts<span class="hljs-punctuation">)</span> 파일을 읽음                         │
│   - 어떤 프로젝트/서브모듈들이 빌드에 참여하는지 결정             │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ <span class="hljs-number">2</span>. Configuration <span class="hljs-punctuation">(</span>구성/설정 단계<span class="hljs-punctuation">)</span>                            │
│   - 참여하는 모든 프로젝트의 build.gradle<span class="hljs-punctuation">(</span>.kts<span class="hljs-punctuation">)</span> 스크립트를 실행   │
│   - Task 객체를 메모리에 생성하고, Task 간의 의존 그래프<span class="hljs-punctuation">(</span>DAG<span class="hljs-punctuation">)</span> 구성 │
│   - ※ 주의: Task 내부의 doFirst/doLast 밖 코드는 이때 무조건 실행됨│

                               │

┌─────────────────────────────────────────────────────────────┐

└─────────────────────────────────────────────────────────────┘</code></pre>

<h2>3. 의존성 스코프(Configuration) 이해하기</h2>
<p>Gradle에서 라이브러리를 가져올 때 선언하는 키워드들은 라이브러리가 <strong>컴파일 시점에 필요한지, 런타임에 필요한지, 그리고 하위 모듈로 전파되는지</strong>를 결정한다.</p>
<pre><code class="hljs">                    ┌── compileOnly <span class="hljs-punctuation">(</span>컴파일 때만 필요, Jar 배포 시 제외 e.g. Lombok<span class="hljs-punctuation">)</span>
                    │
                    ├── runtimeOnly <span class="hljs-punctuation">(</span>실행 때만 필요 e.g. DB JDBC Driver<span class="hljs-punctuation">)</span>
의존성 스코프 종류 ───┼── implementation <span class="hljs-punctuation">(</span>내부 구현용, 외부 모듈로 전파 차단 ➔ 컴파일 속도 향상<span class="hljs-punctuation">)</span>
                    │
                    └── api <span class="hljs-punctuation">(</span>외부 모듈로 의존성 전파 ➔ 공통 인터페이스 모듈용<span class="hljs-punctuation">)</span></code></pre>
<h3><code>implementation</code> vs <code>api</code>의 결정적 차이</h3>
<p>멀티모듈을 설계할 때 가장 중요한 개념이다.</p>
<pre><code class="hljs">[Module <span class="hljs-keyword">A</span>] ──<span class="hljs-punctuation">(</span>의존<span class="hljs-punctuation">)</span>──▶ [Module B] ──<span class="hljs-punctuation">(</span>의존<span class="hljs-punctuation">)</span>──▶ [Module C <span class="hljs-punctuation">(</span>e.g. Gson<span class="hljs-punctuation">)</span>]</code></pre>
<ul>
<li><strong><code>Module B</code>가 <code>api(project(&quot;:Module-C&quot;))</code>를 사용한 경우</strong>:<ul>
<li><code>Module A</code>에서도 <code>Module C</code>(Gson)의 클래스를 직접 import해서 쓸 수 있다.</li>
<li><strong>단점</strong>: <code>Module C</code>의 코드가 1줄이라도 바뀌면 <code>Module B</code>뿐만 아니라 <code>Module A</code>까지 연쇄적으로 재컴파일되어 빌드 시간이 길어진다.</li>
</ul>
</li>
<li><strong><code>Module B</code>가 <code>implementation(project(&quot;:Module-C&quot;))</code>를 사용한 경우</strong>:<ul>
<li><code>Module B</code> 내부에서만 <code>Module C</code>를 쓰고, <code>Module A</code>에는 <code>Module C</code>가 노출되지 않는다 (<code>Module A</code>에서 Gson import 불가).</li>
<li><strong>장점</strong>: <code>Module C</code>의 내부 구현이 바뀌어도 <code>Module A</code>는 재컴파일되지 않으므로 <strong>빌드 속도가 비약적으로 향상</strong>된다. 캡슐화가 잘 지켜진다.</li>
</ul>
</li>
</ul>
<blockquote>
<p><strong>실무 원칙</strong>: 기본적으로 무조건 <strong><code>implementation</code></strong> 을 사용하고, 해당 라이브러리의 타입을 외부에 반환 타입이나 파라미터로 공개해야 하는 공통 API 모듈에서만 제한적으로 <strong><code>api</code></strong> 를 사용한다.</p>
</blockquote>

<h2>4. 모던 Gradle: Version Catalog (<code>libs.versions.toml</code>)</h2>
<p>과거에는 여러 모듈의 라이브러리 버전을 맞추기 위해 <code>ext</code> 블록이나 <code>buildSrc</code>를 썼지만, Gradle 7.4+부터는 표준화된 <strong>Version Catalog (<code>libs.versions.toml</code>)</strong> 방식을 사용한다.</p>
<p><code>gradle/libs.versions.toml</code> 파일에 버전과 라이브러리를 중앙 집중 관리한다.</p>

<h2>5. 실무 프로젝트 설계 패턴 3가지 (멀티모듈 아키텍처)</h2>
<p>실무에서 서비스가 커지면 단일 모듈(Monolith Module)의 한계에 부딪힌다. 
도메인과 계층을 분리하는 대표적인 <strong>Gradle 멀티모듈 설계 패턴 3가지</strong>를 살펴본다.</p>
<hr>
<h3>패턴 1: 계층형 멀티모듈 구조 (Layered Multi-Module)</h3>

<ul>
<li>데이터베이스를 MySQL에서 MongoDB로 바꾸거나 JPA에서 R2DBC로 교체해도 <code>order-domain</code> 코드는 <strong>단 1글자도 수정되지 않는다</strong>.</li>
<li>프레임워크가 없는 순수 자바 단위 테스트(Unit Test)를 작성할 수 있어 테스트 실행 속도가 0.1초 단위로 끝난다.</li>
</ul>
<hr>
<h2>6. 멀티모듈 빌드 속도를 3배 빠르게 만드는 실무 최적화 팁</h2>
<h3>1) <code>gradle.properties</code> 튜닝</h3>
<p>프로젝트 루트의 <code>gradle.properties</code>에 아래 옵션들을 활성화한다.</p>
<pre><code class="hljs language-properties"><span class="hljs-comment"># 데몬 프로세스 재사용으로 JVM 웜업 시간 단축</span>
<span class="hljs-attr">org.gradle.daemon</span>=<span class="hljs-string">true</span>
<span class="hljs-comment">
# 독립적인 모듈들을 병렬로 동시 빌드 (코어 수 활용)</span>
<span class="hljs-attr">org.gradle.parallel</span>=<span class="hljs-string">true</span>
<span class="hljs-comment">
# 이전 빌드 결과물을 캐싱하여 변경이 없는 작업 스킵</span>
<span class="hljs-attr">org.gradle.caching</span>=<span class="hljs-string">true</span>
<span class="hljs-comment">
# 빌드 시 JVM 힙 메모리 넉넉히 할당</span>
<span class="hljs-attr">org.gradle.jvmargs</span>=<span class="hljs-string">-Xmx4g -XX:+UseParallelGC -XX:MaxMetaspaceSize=512m</span>
<span class="hljs-comment">
# 설정 단계 캐싱 (Gradle 8+)</span>
<span class="hljs-attr">org.gradle.configuration-cache</span>=<span class="hljs-string">true</span></code></pre>
<h3>2) 빌드 캐시와 증분 빌드 확인하기</h3>
<p>빌드 실행 시 Task 옆에 표시되는 라벨의 의미를 알고 있어야 한다:</p>
<ul>
<li><code>&gt; Task :core:compileJava UP-TO-DATE</code>: 소스 코드가 바뀌지 않아 컴파일을 스킵함.</li>
<li><code>&gt; Task :core:compileJava FROM-CACHE</code>: 로컬 또는 원격 빌드 캐시에서 결과물을 바로 꺼내옴.</li>
<li><code>&gt; Task :core:compileJava</code>: 실제로 재컴파일을 수행함.</li>
</ul>
<hr>
<h2>7. 흔한 실수와 트러블슈팅</h2>
<table>
<thead>
<tr>
<th>문제 상황</th>
<th>원인</th>
<th>해결책</th>
</tr>
</thead>
<tbody><tr>
<td><strong><code>No main class specified</code> 에러</strong></td>
<td>도메인이나 공통 라이브러리 서브모듈에 <code>bootJar</code>가 켜져 있어 main 메서드를 찾으려고 함</td>
<td>서브모듈의 <code>build.gradle.kts</code>에 <code>tasks.bootJar { enabled = false }</code>, <code>tasks.jar { enabled = true }</code> 설정</td>
</tr>
<tr>
<td><strong>순환 참조 (<code>Circular dependency</code>)</strong></td>
<td><code>Module A</code>가 <code>Module B</code>를 참조하고, <code>Module B</code>가 <code>Module A</code>를 참조함</td>
<td>공통 인터페이스나 DTO를 제3의 <code>core</code> 모듈로 추출하여 단방향 흐름 유지</td>
</tr>
<tr>
<td><strong>버전 충돌 (<code>NoSuchMethodError</code>)</strong></td>
<td>서브모듈마다 라이브러리 버전이 제각각 선언됨</td>
<td><code>libs.versions.toml</code> (Version Catalog)을 통해 버전을 단일 지점에서 통제</td>
</tr>
<tr>
<td><strong>불필요한 전체 재컴파일</strong></td>
<td>하위 모듈 의존성을 <code>api</code>로 무분별하게 선언</td>
<td>기본적으로 <code>implementation</code>을 사용하여 변경 전파 격리</td>
</tr>
</tbody></table>
<hr>
<h2>연습</h2>
<ol>
<li><code>settings.gradle.kts</code>를 작성하여 <code>core</code>, <code>domain</code>, <code>api</code> 3개 모듈을 갖는 계층형 멀티모듈 프로젝트를 구성해 본다.</li>
<li><code>domain</code> 모듈에서 <code>bootJar</code>를 비활성화하고 순수 <code>jar</code>로 빌드되도록 설정한 뒤, <code>api</code> 모듈에서 이를 주입받아 Spring Boot 애플리케이션을 기동해 본다.</li>
<li><code>gradle/libs.versions.toml</code> 파일을 생성하여 Spring Boot 및 QueryDSL 버전을 정의하고 멀티모듈 전체에서 중앙 집중식으로 참조해 본다.</li>
</ol>
