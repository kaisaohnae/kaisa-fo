3:T2895,<h1>IAM 역할과 최소 권한 설계</h1>
<blockquote>
<p>요약: 사람·워크로드에 임시 역할만 맡기고, 정책의 Action과 Resource를 좁혀 최소 권한을 설계하는 방법을 정리한다.</p>
</blockquote>
<hr>
<h2>1. 언제 역할을 쓰는가</h2>
<p>IAM은 계정 안의 출입문이다. 사용자에게 장기 키를 나눠 주는 방식은 유출과 회수가 어렵다. <strong>역할(Role)</strong> 을 맡으면 STS가 짧은 자격을 준다. STS는 Security Token Service다.</p>
<p>역할을 쓰는 경우:</p>
<ul>
<li>EC2, ECS 태스크, Lambda가 S3·RDS 시크릿에 접근할 때</li>
<li>GitHub Actions 등 CI가 배포할 때 (OIDC로 Assume)</li>
<li>사람이 프로덕션에 들어갈 때 (SSO 또는 역할 전환 + MFA)</li>
</ul>
<p>장기 액세스 키가 남는 경우:</p>
<ul>
<li>로컬 실험용 IAM 사용자 키. 범위 최소, 회전, 저장소 금지</li>
<li>레거시 도구가 역할 Assume을 못할 때. 마이그레이션 대상으로 표시</li>
</ul>
<p>루트 키는 해당 없다. 발급하지 않는다.</p>
<hr>
<h2>2. 핵심 개념</h2>
<table>
<thead>
<tr>
<th>용어</th>
<th>의미</th>

<p>정책의 핵심은 네 칸이다. Effect, Action, Resource, Condition. 최소 권한은 <strong>Action과 Resource를 좁히는 일</strong>이다.</p>
<p>관리형 <code>AdministratorAccess</code>는 학습용 계정에서도 짧게만 쓴다. <code>AmazonS3FullAccess</code>도 모든 버킷이다. 앱에는 과하다.</p>
<p>신뢰 정책이 느슨하면 아무 계정의 역할이 우리 역할을 맡는다. <code>Principal</code>을 구체 ARN으로 둔다. <code>sts:ExternalId</code>나 OIDC <code>sub</code> 조건을 CI에 건다.</p>
<hr>

<hr>
<h2>4. 운영 시 주의</h2>
<p><strong>키.</strong> 저장소에 <code>AKIA…</code>가 커밋되면 즉시 비활성화한다. 프론트엔드·모바일 바이너리에 키를 넣지 않는다. 브라우저가 S3에 쓰려면 서명 URL 또는 Cognito 같은 임시 자격이다.</p>
<p><strong>와일드카드.</strong> <code>Resource: &quot;*&quot;</code> + <code>iam:*</code>, <code>sts:*</code>, <code>s3:*</code> 조합은 사고 대기. 리전 제한 <code>aws:RequestedRegion</code>을 Condition으로 한 겹 더 둘 수 있다.</p>
<p><strong>분석.</strong> IAM Access Analyzer, Access Advisor로 안 쓰는 권한을 줄인다. 처음엔 관리형으로 시작하고, 트래픽이 안정되면 고객 관리형으로 축소한다.</p>
<p><strong>계정 분리.</strong> 가능하면 개발/스테이징/프로덕션 계정을 나눈다. 같은 계정이면 태그 조건과 권한 경계로 환경을 섞지 않는다.</p>
<p><strong>감사.</strong> CloudTrail로 <code>AssumeRole</code>, <code>CreateAccessKey</code>를 본다. 콘솔 로그인은 MFA가 있는지 주기적으로 확인한다.</p>
<p><strong>시크릿.</strong> IAM은 권한이 아니라 비밀번호 저장소가 아니다. DB 암호는 Secrets Manager, 회전에 역할을 묶는다.</p>
<p>인라인 정책은 역할이 늘면 복붙이 된다. 고객 관리형 정책을 재사용하는 편이 감사에 낫다. 한 역할에 정책 10개를 쌓기보다 문서를 합친다. 제한 개수도 있다.</p>
<p><strong>흔한 실수.</strong> <code>AdministratorAccess</code>를 Lambda에 달기, <code>s3:*</code>를 <code>*</code> 리소스에 주기, GitHub PAT와 AWS 키를 같은 <code>.env</code>에 커밋하기. 발견 즉시 키를 폐기한다.</p>
<hr>
<h2>5. 정리</h2>
<p>IAM은 기능이 아니라 <strong>경계</strong>다. “일단 Admin”을 없애는 순간부터 운영이 안정된다. 워크로드는 역할, 사람은 SSO, 정책은 Action·Resource를 좁힌다.</p>
<h3>체크리스트</h3>
<ul>
<li><input disabled="" type="checkbox"> 워크로드에 인스턴스/태스크 역할을 붙인다. 박스 안 액세스 키는 유출 지점이다.</li>
<li><input disabled="" type="checkbox"> 정책 Resource를 버킷·ARN 단위로 좁힌다. <code>*</code>는 설명이 필요한 예외다.</li>
<li><input disabled="" type="checkbox"> CI는 OIDC 역할 Assume을 쓴다. 저장소 시크릿의 장기 키는 회전이 어렵다.</li>
<li><input disabled="" type="checkbox"> 관리자 역할에 MFA 조건을 단다. 비밀번호만으로 승격되지 않게 한다.</li>
<li><input disabled="" type="checkbox"> Access Advisor로 90일 미사용 권한을 줄인다. 권한은 시간이 지나면 늘어만 간다.</li>
</ul>
<h3>연습</h3>
<ol>
<li>위 S3 <code>GetObject</code> 정책을 역할에 달고, 다른 버킷 GET이 거절되는지 확인한다.</li>
<li><code>get-caller-identity</code>로 지금 자격의 ARN이 역할인지 사용자인지 구분한다.</li>
<li>관리형 <code>AmazonS3FullAccess</code>와 고객 관리형 한 버킷 정책을 비교해 Action 개수를 세어 본다.</li>
</ol>
