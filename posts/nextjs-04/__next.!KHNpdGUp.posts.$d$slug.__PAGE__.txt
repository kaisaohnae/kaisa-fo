3:T36e8,<h1>데이터 페칭과 캐시 전략</h1>
<blockquote>
<p>요약: 서버 컴포넌트에서 데이터를 읽고, 캐시할지 매 요청 최신으로 둘지 옵션으로 명시한다.</p>
</blockquote>
<hr>
<h2>1. 왜 이 주제가 필요한가</h2>
<p>화면이 비어 있고 브라우저가 API를 다시 치면, 검색엔진과 SNS 미리보기는 본문을 못 본다. 느리다.</p>
<p>App Router에서는 <strong>Server Component</strong>가 데이터를 먼저 읽는다. HTML에 본문이 담긴 채로 나간다.</p>
<p>문제는 “얼마나 자주 다시 읽느냐”다. 매번 최신이면 서버·원본 API 부하가 커진다. 너무 오래 캐시하면 수정한 글이 안 보인다.</p>
<hr>
<h2>2. 한 줄 규칙</h2>
<p>서버에서 읽고, <code>fetch</code> 옵션을 명시한다.</p>
<p>Next.js 15부터 <code>fetch</code> 기본값은 캐시하지 않음(<code>no-store</code>)이다. 정적 페이지를 만들 때는 <code>cache: &#39;force-cache&#39;</code> 또는 <code>next: {revalidate: N}</code>을 적는다. 팀 표준을 코드에 남긴다.</p>
<hr>
<h2>3. 예제</h2>
<h3>서버에서 fetch</h3>

<p><code>revalidate: 60</code>은 <strong>ISR(Incremental Static Regeneration, 만들어 둔 HTML을 N초 뒤에 다시 생성하는 방식)</strong> 에 가깝다. 60초 안은 캐시, 이후 요청을 계기로 백그라운드에서 갱신한다.</p>
<h3>옵션 치트시트</h3>
<table>
<thead>
<tr>
<th>옵션</th>
<th>의미</th>
</tr>
</thead>
<tbody><tr>
<td><code>cache: &#39;force-cache&#39;</code></td>
<td>가능하면 캐시. 빌드 때 읽기에 가깝다</td>
</tr>
<tr>
<td><code>cache: &#39;no-store&#39;</code></td>
<td>요청마다 원본을 친다</td>
</tr>
<tr>
<td><code>next: {revalidate: N}</code></td>
<td>N초 후 재검증</td>
</tr>
<tr>
<td><code>next: {tags: [&#39;post&#39;]}</code></td>
<td>태그로 묶었다가 한 번에 무효화</td>
</tr>
</tbody></table>
<p>페이지 단위로 재검증 주기를 정할 수도 있다.</p>
<pre><code class="hljs language-tsx"><span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> revalidate = <span class="hljs-number">60</span>;
<span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> dynamic = <span class="hljs-string">&#x27;force-static&#x27;</span>;</code></pre>
<p><code>cookies()</code>나 <code>headers()</code>를 읽으면 그 라우트는 동적이 된다. 요청마다 달라져야 하는 값이 있을 때만 쓴다.</p>
<h3>태그 무효화</h3>
<p>글 저장 후 목록·상세 캐시를 깨고 싶을 때 태그를 쓴다.</p>
<pre><code class="hljs language-ts"><span class="hljs-comment">// app/posts/actions.ts</span>
<span class="hljs-string">&#x27;use server&#x27;</span>;

<span class="hljs-keyword">import</span> {revalidateTag} <span class="hljs-keyword">from</span> <span class="hljs-string">&#x27;next/cache&#x27;</span>;

<span class="hljs-keyword">export</span> <span class="hljs-keyword">async</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">afterSavePost</span>(<span class="hljs-params"></span>) {
  <span class="hljs-comment">// Next.js 15: revalidateTag(&#x27;post&#x27;)</span>
  <span class="hljs-comment">// Next.js 16: 두 번째 인자(캐시 프로파일)가 필요하다</span>
  <span class="hljs-title function_">revalidateTag</span>(<span class="hljs-string">&#x27;post&#x27;</span>, <span class="hljs-string">&#x27;max&#x27;</span>);
}</code></pre>
<p>정적 내보내기(<code>output: &#39;export&#39;</code>)에서는 런타임 재검증이 없다. 빌드할 때 읽을 수 있는 데이터만 맞다. 로컬 마크다운, 공개 API가 그 예다.</p>
<h3>로컬 파일</h3>
<p>블로그·문서 사이트는 파일을 서버에서 읽는다.</p>
<pre><code class="hljs language-ts"><span class="hljs-comment">// lib/markdown.ts</span>
<span class="hljs-keyword">import</span> fs <span class="hljs-keyword">from</span> <span class="hljs-string">&#x27;node:fs&#x27;</span>;

<p>이 코드는 Server Component나 <code>lib</code>에서만 호출한다. Client에 import하지 않는다.</p>
<h3>클라이언트 페칭은 언제</h3>
<p>서버가 담당하기 어려운 경우만 Client에서 가져온다.</p>
<ul>
<li>로그인한 사용자만의 실시간 숫자</li>
<li>무한 스크롤, 입력할 때마다 바뀌는 검색</li>
<li><code>localStorage</code> 등 브라우저 값에 의존하는 요청</li>
</ul>
<p>초기 본문·목록·SEO에 필요한 HTML은 서버가 채운다. 그 위에 검색창만 Client로 얹는다.</p>

<h2>4. 흔한 실수</h2>
<table>
<thead>

<th>실수</th>
<th>결과</th>
<th>대안</th>

<td><code>fetch</code> 옵션을 안 적는다</td>

<td><code>cache</code> / <code>revalidate</code> / <code>tags</code>를 명시</td>

<td>빌드 시점에 읽히는 소스만</td>
</tr>
<tr>
<td>Client에서 시크릿 헤더 fetch</td>

<td>서버 <code>lib</code> + props</td>
</tr>

<h2>정리</h2>
<p>데이터는 서버에서 읽는다. 캐시 여부는 추측하지 않고 옵션으로 적는다.</p>
<p>공개 문서는 빌드 때 읽고, 개인화·검색 타이핑만 클라이언트로 남긴다. 정적 호스팅이면 “빌드 타임에 존재하는 데이터”가 유일한 소스다.</p>
<hr>
<h2>연습</h2>
<ol>
<li>같은 URL에 <code>revalidate: 60</code> fetch와 <code>cache: &#39;no-store&#39;</code> fetch를 번갈아 넣고, 빌드 로그의 정적/동적 표시를 비교한다.</li>
<li><code>content/</code> 마크다운을 읽어 목록 페이지를 만든다.</li>
<li>현재 배포가 <code>export</code>면 런타임 재검증을 빼고, 데이터 소스를 “빌드 때 읽기”로만 정리한다.</li>
</ol>
