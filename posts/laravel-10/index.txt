<hr>
<h2>2. 배포가 하는 일</h2>
<p>코드만 올리는 것으로 끝나지 않는다. 의존성, 마이그레이션, 설정 캐시, 프론트 빌드, <strong>워커·스케줄러</strong>가 한 세트다.</p>
<pre><code class="hljs language-bash">composer install --no-dev --optimize-autoloader
php artisan migrate --force
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan event:cache
php artisan storage:<span class="hljs-built_in">link</span>
npm ci &amp;&amp; npm run build</code></pre>
<p><code>--force</code>는 운영에서 마이그레이션 확인 프롬프트를 건너뛴다. CI/배포 스크립트에서만 쓰고, 로컬 습관으로 두지 않는다.</p>
<p>무중단이면 심링크 릴리즈(Envoyer 스타일)나 <code>artisan down</code>을 검토한다. Horizon을 쓰면 배포 후 <code>horizon:terminate</code>로 워커가 새 코드를 물게 한다. 웹만 재시작하고 워커가 옛 코드를 붙잡고 있으면 Job이 옛날 버그로 돈다.</p>
<p>큐 워커, Horizon, <code>schedule:run</code>, Reverb는 웹 PHP-FPM과 <strong>별도 프로세스</strong>다. 웹 컨테이너만 올리면 메일이 안 가고 cron도 안 돈다.</p>
<hr>
<h2>3. Sail은 로컬용</h2>
<p><strong>Sail</strong>은 Laravel 공식 Docker Compose다. PHP·MySQL·Redis 버전을 팀에서 맞춘다. <code>./vendor/bin/sail</code>이 <code>php</code>/<code>composer</code>를 컨테이너 안에서 실행한다.</p>
<pre><code class="hljs language-bash">php artisan sail:install
./vendor/bin/sail up -d
./vendor/bin/sail artisan migrate
./vendor/bin/sail npm run dev</code></pre>
<p>운영에 Sail 이미지를 그대로 올리지 않는 편이 일반적이다. 개발 도구·볼륨 마운트·루트에 가까운 관례가 남아 있다. 운영은 PHP-FPM + Nginx/Caddy Dockerfile을 따로 둔다.</p>
<hr>
<h2>4. 운영 이미지 스케치</h2>
<pre><code class="hljs language-dockerfile"><span class="hljs-keyword">FROM</span> serversideup/php:<span class="hljs-number">8.3</span>-fpm-nginx AS base

<span class="hljs-keyword">WORKDIR</span><span class="language-bash"> /var/www/html</span>
<span class="hljs-keyword">COPY</span><span class="language-bash"> --<span class="hljs-built_in">chown</span>=www-data:www-data . .</span>
<span class="hljs-keyword">RUN</span><span class="language-bash"> composer install --no-dev --optimize-autoloader \
 &amp;&amp; php artisan storage:<span class="hljs-built_in">link</span> \
 &amp;&amp; npm ci &amp;&amp; npm run build \
 &amp;&amp; php artisan view:cache</span></code></pre>
<p>권장:</p>
<ul>
<li>non-root 유저</li>
<li>헬스체크 <code>GET /up</code> (Laravel 11+ <code>bootstrap/app.php</code>의 <code>health</code>)</li>
<li>웹 / 큐 / 스케줄러를 프로세스 또는 Deployment로 분리</li>
<li><code>storage</code>와 <code>bootstrap/cache</code>는 쓰기 가능, 코드는 읽기 전용에 가깝게</li>
</ul>
<p>Kubernetes면 웹·워커·스케줄을 레플리카로 나눈다. 스케줄은 <code>onOneServer</code> 또는 단일 cron Job만 돌린다. 세 파드가 모두 <code>schedule:run</code>을 치면 일일 리포트가 세 번 나간다.</p>
<hr>
<h2>5. Forge, Vapor, 그 외</h2>
<p><strong>Laravel Forge</strong>는 VPS에 Nginx, SSL, 배포 스크립트, 데몬(워커)을 깔아 주는 서비스다. 전통 서버 운영에 잘 맞는다.</p>
<p><strong>Laravel Vapor</strong>는 AWS Lambda 위에 Laravel을 올리는 서버리스다. 로컬 디스크가 잠깐이고, 롱런 워커 모델이 서버와 다르다. 큐·세션·파일은 AWS 서비스에 맞춰 다시 설계한다.</p>
<p>공식 Laravel Cloud나 Railway·Render·Fly.io 같은 PaaS도 있다. 공통은 “웹만 띄우면 끝”이 아니라는 점이다.</p>

<span class="hljs-attr">stdout_logfile</span>=/home/app/storage/logs/worker.log</code></pre>
<p><code>--max-time</code>으로 워커를 주기적으로 죽여 메모리 누수를 끊는다. Horizon이면 <code>artisan horizon</code>을 Supervisor가 관리한다.</p>
<pre><code class="hljs language-cron">* * * * * www-data <span class="hljs-built_in">cd</span> /home/app &amp;&amp; php artisan schedule:run &gt;&gt; /dev/null 2&gt;&amp;1</code></pre>
<p>cron이 루트 홈에서 돌면 <code>.env</code>를 못 읽어 스케줄만 조용히 실패한다. <code>cd</code> 경로가 앱 루트인지 확인한다.</p>
<hr>
<h2>7. 파일과 로그</h2>
<p>컨테이너가 재시작되면 로컬 <code>storage/app</code>는 사라질 수 있다. 업로드는 <strong>S3 호환 오브젝트 스토리지</strong>, <code>FILESYSTEM_DISK=s3</code>가 기본에 가깝다. 공개 파일은 CDN, 백업은 DB 스냅샷과 버킷 버전을 같이 본다.</p>
<pre><code class="hljs language-env"><span class="hljs-attr">LOG_CHANNEL</span><span class="hljs-operator">=</span>stack
<span class="hljs-attr">LOG_STACK</span><span class="hljs-operator">=</span>single,stderr</code></pre>
<p>컨테이너는 stdout/stderr로 보내는 편이 수집기가 먹기 쉽다. 예외는 Sentry·Flare 같은 서비스로 보내고, Telescope는 운영 URL에 열어 두지 않는다.</p>
<p><code>/up</code>은 프로세스 생존만 본다. DB·Redis까지 보려면 커스텀 헬스 체크를 추가한다. 앱은 떴는데 Redis가 죽으면 큐·세션이 같이 죽는다.</p>
<hr>
<h2>8. 보안·운영 체크리스트</h2>
<ul>
<li><input disabled="" type="checkbox"> <code>APP_DEBUG=false</code>, HTTPS, HSTS</li>
<li><input disabled="" type="checkbox"> <code>APP_KEY</code> 유출 시 재발급하면 기존 암호화 값이 안 읽힌다는 점을 안다</li>
<li><input disabled="" type="checkbox"> <code>composer audit</code>, <code>.env</code>·프라이빗 버킷 권한</li>
<li><input disabled="" type="checkbox"> 로그인·민감 API throttle</li>
<li><input disabled="" type="checkbox"> CSRF / CORS / Sanctum 도메인이 스테이징과 같은 실수 없이 맞다</li>
<li><input disabled="" type="checkbox"> Filament·관리자 경로에 추가 보호</li>
<li><input disabled="" type="checkbox"> 업로드 MIME·크기 제한</li>
<li><input disabled="" type="checkbox"> 워커·스케줄·Horizon이 배포 후 새 코드로 재기동된다</li>
</ul>
<hr>
<h2>9. 흔한 실수</h2>
<ul>
<li>Sail Compose를 운영에 그대로 올린다.</li>
<li>웹만 배포하고 <code>queue:work</code> / cron을 안 켠다.</li>
<li>이미지에 <code>.env</code>를 COPY한다.</li>
<li><code>config:cache</code> 없이 매 요청 <code>env()</code> — 또는 반대로 로컬에서 route cache를 켠 채 개발한다.</li>
<li><code>storage:link</code>를 빼 업로드 URL이 404가 난다.</li>
</ul>
<hr>
<h2>연습</h2>
<ol>
<li>Sail로 app + MySQL + Redis를 띄운다.</li>
<li>migrate·캐시·<code>npm run build</code>를 배포 스크립트로 적는다.</li>
<li>워커 또는 Horizon을 켜고 Job이 소비되는지 본다.</li>
<li><code>APP_DEBUG=false</code>, <code>/up</code>, 로그(또는 Sentry)를 스테이징에서 확인한다.</li>
<li>위 체크리스트를 통과/미통과로 표시한다.</li>
</ol>
<p>Laravel은 CRUD 생성기를 넘어 검증·인가·큐·캐시·배포가 한 줄로 이어진다. 입력은 Form Request, 출력은 Resource, 권한은 Policy, 느린 일은 afterCommit Job, 워커와 스케줄은 배포의 일부다.</p>
