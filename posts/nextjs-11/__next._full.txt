24:T5d4f,<h1>Next.js 배포 전략 비교 — Vercel, Docker, 정적 내보내기, AWS 인프라</h1>
<blockquote>
<p>요약: Vercel 서버리스, Standalone Docker 컨테이너, Static Export(S3/CloudFront), OpenNext(AWS Lambda) 등 Next.js의 4가지 주요 배포 방식별 아키텍처와 장단점을 비교하고 최적의 선택 가이드를 제시한다.</p>
</blockquote>
<hr>
<h2>1. Next.js 배포가 다른 프론트엔드와 다른 이유</h2>
<p>전통적인 React SPA(Vite, CRA)는 빌드 결과물이 <code>index.html</code>, <code>bundle.js</code>, CSS 파일뿐이므로 단순한 정적 파일 스토리지(S3, Nginx, GitHub Pages)에 올리면 끝났다.</p>
<p>하지만 <strong>Next.js(App Router)</strong> 는 프론트엔드 프레임워크이면서 동시에 <strong>Node.js 서버 런타임</strong>을 내장하고 있다:</p>
<ul>
<li><strong>서버 컴포넌트(RSC)</strong>: 서버에서 React 트리를 렌더링하여 클라이언트에 스트리밍</li>
<li><strong>서버 액션(Server Actions)</strong> &amp; <strong>라우트 핸들러(Route Handlers)</strong>: 백엔드 API 및 Form Mutation 처리</li>
<li><strong>미들웨어(Middleware)</strong>: 요청 라우팅, 인증 쿠키 검증, 리다이렉트</li>
<li><strong>ISR(Incremental Static Regeneration)</strong>: 캐시 무효화 및 백그라운드 페이지 재생성</li>
<li><strong>Image Optimization (<code>next/image</code>)</strong>: 클라이언트 해상도에 맞춘 실시간 이미지 리사이징/WebP 변환</li>
</ul>
<p>이러한 기능들을 실제로 어떻게 운영할 것인가에 따라 <strong>배포 방식과 인프라 아키텍처가 완전히 달라진다</strong>.</p>
<hr>

<h2>3. 방식 1: Vercel (공식 서버리스 PaaS)</h2>
<p>Next.js의 제작사인 Vercel에서 제공하는 올인원 호스팅 서비스다. Git 저장소를 연결하고 Push하면 빌드, CDN 배포, 도메인 연결, SSL 발급, Preview 환경까지 자동으로 구성된다.</p>
<pre><code class="hljs">[<span class="hljs-title class_">User</span> <span class="hljs-title class_">Request</span>] ──▶ [<span class="hljs-title class_">Vercel</span> <span class="hljs-title class_">Global</span> <span class="hljs-title class_">Edge</span> <span class="hljs-title class_">Network</span> (CDN)]
                           │
       ┌───────────────────┴───────────────────┐
       ▼                                       ▼
[<span class="hljs-title class_">Edge</span> <span class="hljs-title class_">Middleware</span>]                      [<span class="hljs-title class_">Serverless</span> <span class="hljs-title class_">Function</span>]
(인증 / 라우팅)                       (RSC / <span class="hljs-title class_">Server</span> <span class="hljs-title class_">Action</span> / ISR)</code></pre>
<h3>장점</h3>
<ol>
<li><strong>Zero Configuration</strong>: 설정 파일이나 Dockerfile 없이 Next.js의 모든 기능(App Router, Server Action, ISR, 이미지 최적화, OTel)이 100% 완벽하게 동작한다.</li>
<li><strong>Preview 배포</strong>: 모든 PR(Pull Request)마다 고유한 독립 URL이 생성되어 팀원 간 QA와 디자인 리뷰가 매우 편하다.</li>
<li><strong>글로벌 엣지 인프라</strong>: 전 세계 CDN과 엣지 함수(Edge Functions)가 기본 연동되어 초기 응답 지연(TTFB)이 가장 짧다.</li>
<li><strong>강력한 관측성</strong>: 웹 바이탈(Core Web Vitals), 실시간 로그, 분석 도구가 대시보드에 내장되어 있다.</li>
</ol>
<h3>단점 및 한계</h3>
<ol>
<li><strong>비용 문제 (Bandwidth / Image Optimization 폭탄)</strong>: 트래픽이 커질수록 대역폭(Bandwidth)과 이미지 최적화 호출당 과금 비용이 급격히 증가한다(기업 엔터프라이즈 플랜은 비용이 상당함).</li>
<li><strong>Cold Start (서버리스 지연)</strong>: 오랫동안 요청이 없던 페이지는 서버리스 함수가 처음 뜰 때 수백 ms~수 초의 콜드 스타트 지연이 발생할 수 있다.</li>
<li><strong>사내망/VPC 연동 한계</strong>: 온프레미스 DB나 내부 사내망(AWS VPC)에 위치한 DB/마이크로서비스에 직접 접근하려면 고정 IP 프록시를 두어야 하므로 구성이 복잡해진다.</li>
<li><strong>실행 시간 제한</strong>: 서버리스 함수당 최대 실행 시간(기본 15초~60초)이 제한되어 있어 장시간 실행되는 배치 작업이나 무거운 데이터 처리가 불가능하다.</li>
</ol>

<h2>4. 방식 2: Self-Hosted Standalone Docker (컨테이너 자체 호스팅)</h2>
<p>사내 인프라(Kubernetes, AWS ECS/EC2, 온프레미스 서버)에 Next.js를 직접 배포할 때 사용하는 <strong>표준 실무 방식</strong>이다.</p>
<p>Next.js의 <code>output: &#39;standalone&#39;</code> 기능을 활성화하면, 빌드 시 수백 MB에 달하는 전체 <code>node_modules</code> 중 <strong>프로덕션 실행에 꼭 필요한 최소 파일만 선별하여 <code>.next/standalone</code> 폴더에 복사</strong>해 준다.</p>
<h3>1) <code>next.config.ts</code> 설정</h3>
<pre><code class="hljs language-typescript"><span class="hljs-keyword">import</span> <span class="hljs-keyword">type</span> { <span class="hljs-title class_">NextConfig</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">&#x27;next&#x27;</span>;

<span class="hljs-keyword">const</span> <span class="hljs-attr">nextConfig</span>: <span class="hljs-title class_">NextConfig</span> = {
  <span class="hljs-attr">output</span>: <span class="hljs-string">&#x27;standalone&#x27;</span>, <span class="hljs-comment">// Standalone 빌드 활성화</span>
};

<span class="hljs-keyword">export</span> <span class="hljs-keyword">default</span> nextConfig;</code></pre>
<h3>2) 경량 멀티 스테이지 <code>Dockerfile</code></h3>
<pre><code class="hljs language-dockerfile"><span class="hljs-comment"># 1단계: 의존성 설치</span>
<span class="hljs-keyword">FROM</span> node:<span class="hljs-number">20</span>-alpine AS deps
<span class="hljs-keyword">RUN</span><span class="language-bash"> apk add --no-cache libc6-compat</span>
<span class="hljs-keyword">WORKDIR</span><span class="language-bash"> /app</span>
<span class="hljs-keyword">COPY</span><span class="language-bash"> package.json package-lock.json ./</span>
<span class="hljs-keyword">RUN</span><span class="language-bash"> npm ci</span>

<span class="hljs-comment"># 2단계: 소스 빌드</span>
<span class="hljs-keyword">FROM</span> node:<span class="hljs-number">20</span>-alpine AS builder
<span class="hljs-keyword">WORKDIR</span><span class="language-bash"> /app</span>
<span class="hljs-keyword">COPY</span><span class="language-bash"> --from=deps /app/node_modules ./node_modules</span>
<span class="hljs-keyword">COPY</span><span class="language-bash"> . .</span>
<span class="hljs-keyword">ENV</span> NEXT_TELEMETRY_DISABLED=<span class="hljs-number">1</span>
<span class="hljs-keyword">ENV</span> NODE_ENV=production
<span class="hljs-keyword">RUN</span><span class="language-bash"> npm run build</span>

<span class="hljs-keyword">WORKDIR</span><span class="language-bash"> /app</span>

<span class="hljs-comment"># 정적 에셋 및 standalone 빌드 결과물 복사</span>

<span class="hljs-keyword">COPY</span><span class="language-bash"> --from=builder --<span class="hljs-built_in">chown</span>=nextjs:nodejs /app/.next/standalone ./</span>
<span class="hljs-keyword">COPY</span><span class="language-bash"> --from=builder --<span class="hljs-built_in">chown</span>=nextjs:nodejs /app/.next/static ./.next/static</span>

<span class="hljs-keyword">EXPOSE</span> <span class="hljs-number">3000</span>

<h3>장점</h3>
<ol>
<li><strong>비용 예측 가능성</strong>: 서버 인스턴스(EC2, 물리 서버) 단위로 비용이 청구되므로 대규모 트래픽 발생 시에도 대역폭 폭탄 요금이 없다.</li>
<li><strong>사내망/VPC 자유로운 연결</strong>: VPC 내부의 PostgreSQL, Redis, Kafka, gRPC 백엔드와 초고속 내부 통신이 가능하다.</li>
<li><strong>Cold Start 없음</strong>: Node.js 상시 구동 프로세스(<code>node server.js</code>)이므로 콜드 스타트 없이 항상 일정한 빠른 응답 속도를 유지한다.</li>
<li><strong>실행 환경의 완전한 통제권</strong>: 메모리, CPU, 프로세스 클러스터링(PM2), 모니터링 에이전트(Datadog, Prometheus)를 원하는 대로 설치하고 커스텀할 수 있다.</li>
</ol>
<h3>단점 및 한계</h3>
<ol>
<li><strong>인프라 운영 비용 (DevOps 리소스)</strong>: 로드밸런서(ALB), SSL 인증서 갱신, 무중단 배포(Rolling/Blue-Green), 오토스케일링을 직접 구축하고 관리해야 한다.</li>
<li><strong>멀티 인스턴스 시 ISR 캐시 동기화 필요</strong>: 컨테이너가 3대로 오토스케일링되면, 1번 서버에서 갱신된 ISR 캐시 파일이 2, 3번 서버에는 반영되지 않는다. 이를 해결하려면 공유 스토리지(Redis / S3 Cache Handler)를 별도로 붙여야 한다.</li>
<li><strong>이미지 최적화 부하</strong>: <code>next/image</code> 리사이징 연산이 Node.js CPU를 직접 소모하므로 트래픽이 많을 때는 이미지 최적화 전용 CDN이나 별도 서비스를 두는 것이 안전하다.</li>
</ol>

<h2>5. 방식 3: Static Export (정적 내보내기 / S3 + CloudFront)</h2>
<p>Next.js를 순수한 정적 HTML/CSS/JS 파일들로 추출하여 웹 서버(Nginx)나 클라우드 스토리지(AWS S3 + CloudFront, GitHub Pages, Cloudflare Pages)에 올리는 방식이다.</p>
<h3>1) <code>next.config.ts</code> 설정</h3>
<pre><code class="hljs language-typescript"><span class="hljs-keyword">import</span> <span class="hljs-keyword">type</span> { <span class="hljs-title class_">NextConfig</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">&#x27;next&#x27;</span>;

  <span class="hljs-attr">images</span>: {
    <span class="hljs-attr">unoptimized</span>: <span class="hljs-literal">true</span>, <span class="hljs-comment">// Node 서버가 없으므로 실시간 이미지 리사이징 끔</span>

<pre><code class="hljs language-bash">npm run build
<span class="hljs-comment"># 빌드가 완료되면 프로젝트 루트의 /out 디렉토리에 index.html, posts.html 등이 생성됨</span></code></pre>
<h3>장점</h3>
<ol>
<li><strong>압도적인 저비용 &amp; 가성비</strong>: AWS S3 + CloudFront나 Cloudflare Pages를 이용하면 월 수백만 뷰 사이트도 커피 몇 잔 가격(거의 0원)으로 운영 가능하다.</li>
<li><strong>무한한 트래픽 확장성(Scalability)</strong>: 글로벌 CDN 엣지에서 정적 캐시 파일만 응답하므로 서버 다운(Server Crash) 개념이 아예 없다.</li>
<li><strong>최고 수준의 보안</strong>: 백엔드 Node.js 서버 런타임 자체가 존재하지 않으므로 서버 침투나 RCE(원격 코드 실행) 취약점 위험이 0%다.</li>
</ol>

<h2>6. 방식 4: AWS Serverless (OpenNext / SST / SST v3)</h2>
<p>Vercel의 종속성과 고비용을 피하면서도 서버리스의 장점을 내 AWS 계정(AWS Lambda, CloudFront, S3)으로 그대로 가져오기 위한 오픈소스 프레임워크 기반 배포 방식이다.</p>
<pre><code class="hljs">[<span class="hljs-title class_">User</span> <span class="hljs-title class_">Request</span>] ──▶ [AWS <span class="hljs-title class_">CloudFront</span> (CDN)]
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
[<span class="hljs-title class_">S3</span> <span class="hljs-title class_">Bucket</span>]        [<span class="hljs-title class_">Lambda</span> <span class="hljs-title class_">Edge</span>]       [AWS <span class="hljs-title class_">Lambda</span> (<span class="hljs-title class_">Server</span>)]
(정적 HTML/JS/CSS) (미들웨어 / 라우팅)   (RSC / <span class="hljs-title class_">Server</span> <span class="hljs-title class_">Action</span> / ISR)
                                               │
                                               ▼
                                      [<span class="hljs-title class_">DynamoDB</span> / <span class="hljs-title class_">S3</span>]
                                      (ISR 캐시 저장소)</code></pre>
<h3>장점</h3>
<ol>
<li><strong>내 AWS 계정 안에서 동작</strong>: 회사 AWS 계정의 IAM, VPC, 보안 정책을 그대로 준수할 수 있다.</li>
<li><strong>비용 절감</strong>: Vercel의 비싼 대역폭 요금 대신 AWS의 순수 인프라 원가(AWS Lambda + CloudFront)만 지불하므로 트래픽이 많을 때 수백만 원 단위의 비용이 절감된다.</li>
<li><strong>자동 분할 아키텍처</strong>: OpenNext는 Next.js 빌드 산출물을 정적 파일(S3), 미들웨어(Lambda@Edge), 서버 로직(Lambda)으로 자동 분리하여 배포해 준다.</li>
</ol>
<h3>단점 및 한계</h3>
<ol>
<li><strong>Next.js 신규 기능 지원 시차</strong>: Next.js 새 버전이 출시되었을 때 OpenNext 오픈소스 커뮤니티가 이를 지원하기까지 약간의 딜레이가 발생할 수 있다.</li>
<li><strong>초기 인프라 구축 난이도</strong>: Terraform이나 SST, AWS CDK 등 IaC(Infrastructure as Code) 지식이 요구된다.</li>
</ol>

<h2>9. 실무 체크리스트</h2>
<ul>
<li><input disabled="" type="checkbox"> <strong>환경변수 분리</strong>: 브라우저에 노출되어도 되는 값만 <code>NEXT_PUBLIC_</code> 접두사를 붙였는가?</li>
<li><input disabled="" type="checkbox"> <strong>빌드 산출물 최적화</strong>: Docker 배포 시 <code>next.config.ts</code>에 <code>output: &#39;standalone&#39;</code>을 명시했는가?</li>
<li><input disabled="" type="checkbox"> <strong>Static Export 제약 확인</strong>: <code>output: &#39;export&#39;</code> 사용 시 <code>images.unoptimized: true</code>와 dynamic route 핸들러 제약을 확인했는가?</li>
<li><input disabled="" type="checkbox"> <strong>캐시 헤더 점검</strong>: <code>public/</code> 정적 파일 및 <code>_next/static/</code> 파일에 <code>Cache-Control: public, max-age=31536000, immutable</code> 헤더가 설정되어 있는가?</li>
