3:T2e8d,<h1>상태 관리·아키텍처·모듈화</h1>
<blockquote>
<p>요약: 전역 상태를 최소화하고, 기능 단위 폴더와 Context·Zustand 선택 기준을 정리한다.</p>
</blockquote>
<hr>
<h2>1. 왜 전역을 늦게 쓰나</h2>
<p>앱이 커지면 “일단 Redux”로 가기 쉽다. RN 신규 프로젝트에서 가장 흔한 실수다. 대부분은 로컬 상태와 서버 캐시면 된다.</p>
<p>전역은 <strong>멀리 떨어진 화면이 같은 클라이언트 값을 써야 할 때</strong>만 연다. 장바구니, 테마, 세션이 그 예다. 게시글 목록은 Query에 두고 복제하지 않는다.</p>
<p>폴더를 기능 단위로 나누면 화면 파일이 얇아진다. 라우트는 조립만 한다.</p>
<hr>
<h2>2. 핵심 개념</h2>
<p>상태 배치 순서:</p>
<ol>
<li>로컬 <code>useState</code></li>
<li>라우트 파라미터 (공유·복원 가능한 UI)</li>
<li>React Query (서버 상태)</li>
<li>Context (드물고 천천히 바뀌는 값: theme, auth)</li>
<li>Zustand (클라이언트 전역이 명확할 때)</li>
<li>Redux Toolkit (팀 표준이거나 복잡한 클라이언트 워크플로)</li>
</ol>
<p>Context는 value가 바뀔 때마다 구독 컴포넌트가 다시 그린다. 스크롤 위치, 매 키입력은 넣지 않는다.</p>
<p>Zustand는 셀렉터로 필요한 조각만 구독한다. persist는 AsyncStorage로 충분하다. <strong>토큰은 persist 금지.</strong> SecureStore + Auth 흐름이다.</p>
<p>에러 경계는 라우트 단위로 나눈다. 한 화면 크래시가 앱 전체 흰 화면이 되지 않게 한다.</p>
<p>환경은 <code>app.config.ts</code>와 EAS 프로파일로 나눈다. 번들 ID와 API URL을 섞지 않는다.</p>
<hr>

<h2>5. 정리</h2>
<p>아키텍처는 라이브러리 선택이 아니다. <strong>상태의 원본을 어디에 둘지</strong>를 먼저 정하는 일이다.</p>
<ul>
<li>전역은 최소. Feature 폴더가 경계다.</li>
<li>Context는 테마·세션. Zustand는 장바구니류.</li>
<li>dev/staging/prod는 설정과 번들 ID로 분리한다.</li>
</ul>
<h2>연습</h2>
<ol>
<li><code>posts</code>를 Feature 폴더로 옮긴다.</li>
<li>Zustand로 장바구니 또는 최근 검색어를 persist한다.</li>
<li>Theme Context로 라이트/다크를 토글한다.</li>
<li>라우트 단위 ErrorBoundary를 추가한다.</li>
</ol>
