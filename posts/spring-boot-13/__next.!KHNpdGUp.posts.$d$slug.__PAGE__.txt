<blockquote>
<p>요약: 영속성 컨텍스트 생명주기, 변경 감지, N+1 문제 해결(Fetch Join vs EntityGraph vs BatchSize), 컬렉션 페이징 한계, 낙관적/비관적 락, OSIV 전략을 이해한다.</p>

<h2>1. ORM의 본질과 패러다임의 불일치</h2>
<p>객체지향 언어는 <strong>추상화, 캡슐화, 상속, 다형성</strong>을 통해 유연한 도메인 모델을 만드는 것이 목표이고, 관계형 데이터베이스(RDB)는 <strong>데이터의 정규화와 무결성, 집합 중심의 효율적인 조회</strong>가 목표다. 이 둘 사이에는 태생적인 <strong>패러다임의 불일치(Paradigm Mismatch)</strong> 가 존재한다.</p>
<table>
<thead>
<tr>
<th>관점</th>
<th>객체지향 (Java)</th>
<th>관계형 데이터베이스 (RDB)</th>
</tr>
</thead>
<tbody><tr>
<td><strong>지향점</strong></td>
<td>추상화, 캡슐화, 다형성, 객체 간 참조</td>
<td>데이터 무결성, 정규화, 테이블 간 외래키(FK) 조인</td>
</tr>
<tr>
<td><strong>연관관계</strong></td>
<td><strong>단방향 참조</strong> (<code>order.getMember()</code>)</td>
<td><strong>양방향 조인</strong> (<code>JOIN ON order.member_id = member.id</code>)</td>
</tr>
<tr>
<td><strong>식별자</strong></td>
<td>객체 동일성 (<code>==</code>, 메모리 주소)</td>
<td>기본키 (Primary Key, 테이블 레코드 고유값)</td>
</tr>
<tr>
<td><strong>데이터 탐색</strong></td>
<td>객체 그래프 탐색 (<code>order.getDelivery().getAddress()</code>)</td>
<td>SQL 쿼리로 조회된 레코드셋에 국한</td>
</tr>
<tr>
<td><strong>상속</strong></td>
<td>상속 관계 지원 (<code>extends</code>)</td>
<td>슈퍼타입/서브타입 모델링 (테이블 단편화)</td>
</tr>
</tbody></table>
<p>과거에는 이 차이를 메우기 위해 SQL 매퍼(MyBatis, JdbcTemplate)를 사용하며 개발자가 객체와 테이블 간의 매핑 코드를 일일이 작성했다. </p>
<p><strong>ORM(Object-Relational Mapping)</strong> 은 이 패러다임 불일치를 프레임워크가 중간에서 해결해 주는 기술이다. 자바 진영의 표준 명세가 <strong>JPA(Jakarta Persistence API)</strong> 이며, 가장 널리 쓰이는 표준 구현체가 <strong>Hibernate</strong>다. Spring Boot 환경에서는 이를 한 번 더 편리하게 감싼 <strong>Spring Data JPA</strong>를 주로 사용한다.</p>
<hr>
<h2>2. 영속성 컨텍스트(Persistence Context)의 내부 메커니즘</h2>
<p>영속성 컨텍스트는 <strong>&quot;엔티티를 영구 저장하는 환경&quot;</strong> 이라는 뜻의 논리적인 개념이다. <code>EntityManager</code>를 통해 접근하며, 애플리케이션과 데이터베이스 사이에서 버퍼(Buffer) 및 캐시(Cache) 역할을 수행한다.</p>
<p>스프링 프레임워크에서는 <strong>트랜잭션(<code>@Transactional</code>)의 시작부터 종료까지</strong> 영속성 컨텍스트의 생명주기가 유지된다.</p>
<pre><code class="hljs">[클라이언트 요청] ──▶ [@Transactional Service] 
                              │
                              ▼
                 ┌─────────────────────────────┐
                 │    영속성 컨텍스트 <span class="hljs-punctuation">(</span>EntityManager<span class="hljs-punctuation">)</span>    │
                 │  ┌───────────────────────┐  │
                 │  │ <span class="hljs-number">1</span>차 캐시 <span class="hljs-punctuation">(</span>엔티티 / 스냅샷<span class="hljs-punctuation">)</span>  │  │
                 │  ├───────────────────────┤  │
                 │  │ 쓰기 지연 SQL 저장소       │  │
                 │  └───────────────────────┘  │
                 └──────────────┬──────────────┘
                                │ flush &amp; commit
                                ▼
                         [Database <span class="hljs-punctuation">(</span>RDB<span class="hljs-punctuation">)</span>]</code></pre>
<h3>1) 1차 캐시와 동일성(Identity) 보장</h3>
<p>영속성 컨텍스트 내부에는 엔티티의 <code>@Id</code>(PK) 값을 Key로, 엔티티 인스턴스를 Value로 보관하는 <strong>1차 캐시</strong>가 존재한다.</p>
<pre><code class="hljs language-java"><span class="hljs-comment">// 동일 트랜잭션 내부</span>
<span class="hljs-type">Member</span> <span class="hljs-variable">member1</span> <span class="hljs-operator">=</span> memberRepository.findById(<span class="hljs-number">1L</span>).orElseThrow();
<span class="hljs-type">Member</span> <span class="hljs-variable">member2</span> <span class="hljs-operator">=</span> memberRepository.findById(<span class="hljs-number">1L</span>).orElseThrow();

System.out.println(member1 == member2); <span class="hljs-comment">// true (메모리 주소 일치)</span></code></pre>
<ol>
<li><code>findById(1L)</code> 최초 호출 시 1차 캐시에 없으므로 DB <code>SELECT</code> 쿼리를 실행해 엔티티를 1차 캐시에 저장하고 반환한다.</li>
<li>두 번째 <code>findById(1L)</code> 호출 시 DB 쿼리를 전혀 날리지 않고 <strong>1차 캐시에서 즉시 반환</strong>한다.</li>
<li>동일 트랜잭션 내에서는 <code>==</code> 비교 시 <strong>진정한 객체 동일성(Identity)</strong> 이 보장된다.</li>
</ol>
<h3>2) 쓰기 지연 (Transactional Write-Behind)</h3>
<p><code>em.persist(entity)</code>나 <code>repository.save(entity)</code>를 호출한다고 해서 그 즉시 DB에 <code>INSERT</code> SQL이 나가지 않는다.</p>
<pre><code class="hljs language-java"><span class="hljs-meta">@Transactional</span>
<span class="hljs-keyword">public</span> <span class="hljs-type">void</span> <span class="hljs-title function_">registerMembers</span><span class="hljs-params">()</span> {
    memberRepository.save(<span class="hljs-keyword">new</span> <span class="hljs-title class_">Member</span>(<span class="hljs-string">&quot;A&quot;</span>));
    memberRepository.save(<span class="hljs-keyword">new</span> <span class="hljs-title class_">Member</span>(<span class="hljs-string">&quot;B&quot;</span>));
    memberRepository.save(<span class="hljs-keyword">new</span> <span class="hljs-title class_">Member</span>(<span class="hljs-string">&quot;C&quot;</span>));
    <span class="hljs-comment">// 여기까지 DB에 INSERT 쿼리가 아직 1건도 나가지 않음!</span>
    <span class="hljs-comment">// 쿼리는 영속성 컨텍스트의 &#x27;쓰기 지연 SQL 저장소&#x27;에 차곡차곡 쌓임</span>
    
    <span class="hljs-comment">// 트랜잭션이 끝나는 시점에 모아둔 3개의 INSERT 쿼리가 DB로 한 방에 전송(flush)됨</span>
}</code></pre>
<blockquote>
<p><strong>주의 (IDENTITY 전략 예외)</strong>: MySQL의 <code>AUTO_INCREMENT</code>처럼 <code>@GeneratedValue(strategy = GenerationType.IDENTITY)</code>를 쓰는 경우, PK 값을 DB에 넣기 전까지는 알 수 없다. 영속성 컨텍스트는 1차 캐시의 키로 PK가 필수이기 때문에, <code>IDENTITY</code> 전략에 한해서는 <code>save()</code> 호출 즉시 <code>INSERT</code> 쿼리가 실행되어 쓰기 지연이 발생하지 않는다.</p>
</blockquote>
<h3>3) 변경 감지 (Dirty Checking)의 구체적 동작 원리</h3>
<p>JPA에는 엔티티를 수정하는 <code>update()</code>나 <code>modify()</code> 같은 API가 존재하지 않는다.</p>
<pre><code class="hljs language-java"><span class="hljs-meta">@Transactional</span>
<span class="hljs-keyword">public</span> <span class="hljs-type">void</span> <span class="hljs-title function_">updateMember</span><span class="hljs-params">(Long id, String newName)</span> {
    <span class="hljs-type">Member</span> <span class="hljs-variable">member</span> <span class="hljs-operator">=</span> memberRepository.findById(id).orElseThrow();
    member.changeName(newName); 
    <span class="hljs-comment">// memberRepository.save(member); -&gt; 호출 불필요 (안티패턴)</span>
}</code></pre>
<p><strong>내부 비교 순서:</strong></p>
<ol>
<li><strong>스냅샷 생성</strong>: 1차 캐시에 엔티티가 최초로 로드(조회 또는 영속화)될 때, 그 시점의 상태를 그대로 복제한 <strong>스냅샷(Snapshot)</strong> 을 만든다.</li>
<li><strong>트랜잭션 커밋 시점 <code>flush()</code> 발생</strong>: 트랜잭션이 커밋되기 직전 영속성 컨텍스트가 자동으로 <code>flush()</code>를 실행한다.</li>
<li><strong>상태 비교</strong>: 현재 엔티티의 필드 값과 최초 스냅샷을 1:1로 대조하여 변경된 부분을 찾는다.</li>
<li><strong>UPDATE 쿼리 생성</strong>: 변경 사항이 있으면 <code>UPDATE</code> SQL을 만들어 쓰기 지연 SQL 저장소에 넣고 DB로 전송한다.</li>
</ol>
<h4>변경 감지 시 생성되는 쿼리 특성</h4>
<p>기본적으로 Hibernate는 <strong>엔티티의 모든 컬럼을 UPDATE 대상</strong>으로 삼는다.</p>
<ul>
<li><strong>장점</strong>: SQL 구문이 고정되어 데이터베이스 엔진 차원에서 쿼리를 파싱하고 캐싱(PreparedStatement 재사용)하기 유리하다.</li>
<li><strong>예외 처리 (<code>@DynamicUpdate</code>)</strong>: 테이블의 컬럼 수가 30~50개 이상으로 매우 많고 빈번하게 일부 컬럼만 수정된다면, 엔티티 클래스 위에 <code>@DynamicUpdate</code>를 선언하여 실제 변경된 컬럼만 동적으로 <code>UPDATE</code> 구문을 만들도록 설정할 수 있다.</li>
</ul>
<h3>4) Flush(플러시)의 정확한 개념</h3>
<p><code>flush()</code>는 <strong>영속성 컨텍스트의 변경 내용을 데이터베이스에 동기화(전송)하는 작업</strong>이다.</p>
<ul>
<li><strong>플러시가 일어나는 시점</strong>:<ol>
<li>트랜잭션 커밋 직전 (자동)</li>
<li>JPQL 쿼리 실행 직전 (데이터 정합성을 위해 자동 실행)</li>
<li><code>em.flush()</code> 직접 호출 시</li>
</ol>
</li>
<li><strong>핵심</strong>: 플러시는 DB 트랜잭션을 커밋하는 것이 아니다. 변경된 SQL들을 DB로 보내놓기만 한 상태이므로, 예외가 발생하면 <strong>언제든지 롤백이 가능</strong>하다.</li>
</ul>

<h3>준영속 상태를 다룰 때 주의할 점</h3>
<p><code>em.merge(detachedEntity)</code>를 사용하면 준영속 엔티티의 정보로 새로운 영속 엔티티를 반환하지만, <strong>모든 필드를 덮어쓰기 때문에 값이 없는 필드는 <code>null</code>로 갱신되는 위험</strong>이 있다.</p>
<p>따라서 실무에서는 <code>merge()</code> 대신 <strong>식별자로 엔티티를 조회한 뒤 변경 감지(Dirty Checking)를 통해 필요한 필드만 직접 수정</strong>하는 것이 원칙이다.</p>

<h2>4. 연관관계 매핑과 방향성</h2>
<h3>1) 단방향 매핑 vs 양방향 매핑</h3>
<ul>
<li><strong>단방향 매핑</strong>: 한쪽 엔티티만 상대방을 참조하는 구조 (<code>Order</code> $\rightarrow$ <code>Member</code>). 객체 관계가 단순하고 직관적이다.</li>
<li><strong>양방향 매핑</strong>: 양쪽 엔티티가 서로를 참조하는 구조 (<code>Order</code> $\leftrightarrow$ <code>Member</code>). 조회 편의성은 높지만 복잡도가 크게 증가한다.</li>
</ul>
<blockquote>
<p><strong>실무 대원칙</strong>: 기본적으로 모든 연관관계는 <strong>단방향 매핑</strong>으로 설계한다. 비즈니스 요구사항상 반대편에서의 객체 그래프 탐색이 꼭 필요한 경우에만 제한적으로 양방향 매핑을 추가한다.</p>
</blockquote>
<h3>2) 연관관계의 주인(Owner)과 <code>mappedBy</code></h3>
<p>테이블은 외래키(FK) 1개로 양쪽 조인이 가능하다. 하지만 객체는 참조 변수가 양쪽에 각각 존재한다. 둘 중 <strong>&quot;누가 외래키를 관리(등록/수정)할 것인가&quot;</strong> 를 정해야 하며, 그 주체가 <strong>연관관계의 주인</strong>이다.</p>
<ul>
<li><strong>연관관계의 주인</strong>: 외래키(FK) 컬럼이 존재하는 테이블의 엔티티 (<code>@JoinColumn</code> 사용)</li>
<li><strong>주인이 아닌 쪽</strong>: 조회만 가능 (<code>mappedBy</code> 속성으로 주인의 필드명을 지정)</li>
</ul>
<pre><code class="hljs language-java"><span class="hljs-comment">// [외래키를 가진 연관관계의 주인]</span>
<span class="hljs-meta">@Entity</span>
<span class="hljs-keyword">public</span> <span class="hljs-keyword">class</span> <span class="hljs-title class_">Order</span> {
    <span class="hljs-meta">@Id</span> <span class="hljs-meta">@GeneratedValue</span>
    <span class="hljs-keyword">private</span> Long id;

    <span class="hljs-meta">@ManyToOne(fetch = FetchType.LAZY)</span>
    <span class="hljs-meta">@JoinColumn(name = &quot;member_id&quot;)</span> <span class="hljs-comment">// orders 테이블의 member_id FK 컬럼 관리</span>
    <span class="hljs-keyword">private</span> Member member;
}

<span class="hljs-comment">// [조회만 가능한 주인이 아닌 쪽]</span>
<span class="hljs-meta">@Entity</span>
<span class="hljs-keyword">public</span> <span class="hljs-keyword">class</span> <span class="hljs-title class_">Member</span> {
    <span class="hljs-meta">@Id</span> <span class="hljs-meta">@GeneratedValue</span>
    <span class="hljs-keyword">private</span> Long id;

    <span class="hljs-meta">@OneToMany(mappedBy = &quot;member&quot;)</span> <span class="hljs-comment">// Order 클래스의 &#x27;member&#x27; 필드에 의해 매핑됨</span>
    <span class="hljs-keyword">private</span> <span class="hljs-type">List</span>&lt;Order&gt; <span class="hljs-variable">orders</span> <span class="hljs-operator">=</span> <span class="hljs-keyword">new</span> <span class="hljs-title class_">ArrayList</span>&lt;&gt;();

<h2>5. 지연 로딩(LAZY)과 N+1 문제 해결하기</h2>
<h3>1) 즉시 로딩(EAGER)의 위험성</h3>
<p><code>@ManyToOne(fetch = FetchType.EAGER)</code>로 설정하면 부모 엔티티를 조회할 때 연관된 엔티티를 무조건 함께 조회한다.</p>
<ul>
<li>JPQL을 실행할 때 JPQL은 SQL로 그대로 번역되어 부모만 먼저 조회(<code>SELECT * FROM orders</code>)한 뒤, 뒤늦게 EAGER 설정을 보고 연관 엔티티를 개별 조회(<code>SELECT * FROM member WHERE id = ?</code>)하는 N+1 문제가 무조건 발생한다.</li>
<li><strong>실무 원칙</strong>: 모든 연관관계는 반드시 <strong><code>FetchType.LAZY</code></strong> 로 선언한다.</li>
</ul>
<h3>2) N+1 문제란?</h3>
<p>1번의 쿼리로 N건의 데이터를 조회했을 때, 지연 로딩된 연관 엔티티를 사용하는 과정에서 <strong>추가 쿼리가 N번 더 발생하는 성능 저하 현상</strong>이다.</p>
<pre><code class="hljs language-java"><span class="hljs-comment">// orders 목록 10건 조회 (쿼리 1회)</span>
<span class="hljs-type">List</span>&lt;Order&gt; <span class="hljs-variable">orders</span> <span class="hljs-operator">=</span> orderRepository.findAll();

<span class="hljs-keyword">for</span> (Order order : orders) {
    <span class="hljs-comment">// Member는 프록시 객체 상태 -&gt; 실제 필드 접근 시마다 SELECT 쿼리 발생! (10회)</span>
    System.out.println(order.getMember().getName()); 
}
<span class="hljs-comment">// 총 실행된 쿼리: 1 + 10 = 11회</span></code></pre>
<h3>3) N+1 해결 전략 3가지 비교</h3>
<pre><code class="hljs">                      ┌── <span class="hljs-number">1</span>. Fetch Join <span class="hljs-punctuation">(</span>JPQL INNER JOIN으로 한 방에 로딩<span class="hljs-punctuation">)</span>
                      │
N+<span class="hljs-number">1</span> 해결 <span class="hljs-number">3</span>대 전략 ─────┼── <span class="hljs-number">2</span>. @EntityGraph <span class="hljs-punctuation">(</span>어노테이션 기반 LEFT JOIN 로딩<span class="hljs-punctuation">)</span>
                      │
                      └── <span class="hljs-number">3</span>. default_batch_fetch_size <span class="hljs-punctuation">(</span><span class="hljs-type">IN</span> 쿼리로 묶어서 로딩<span class="hljs-punctuation">)</span></code></pre>
<table>
<thead>
<tr>
<th>해결 방식</th>
<th>코드 형태</th>
<th>장점</th>
<th>단점 및 제약</th>
</tr>
</thead>
<tbody><tr>
<td><strong>Fetch Join</strong></td>
<td><code>select o from Order o join fetch o.member</code></td>
<td>한 번의 SQL 조인으로 실제 엔티티를 모두 조회</td>
<td>둘 이상의 컬렉션(<code>List</code>)을 동시 페치 조인할 수 없음 (<code>MultipleBagFetchException</code>)</td>
</tr>
<tr>
<td><strong><code>@EntityGraph</code></strong></td>
<td><code>@EntityGraph(attributePaths = {&quot;member&quot;})</code></td>
<td>JPQL 없이 Spring Data JPA 인터페이스에 어노테이션으로 적용 가능</td>
<td><code>LEFT OUTER JOIN</code>이 강제되어 조인 비용이 발생할 수 있음</td>
</tr>
<tr>
<td><strong><code>BatchSize</code></strong></td>
<td><code>hibernate.default_batch_fetch_size: 100</code></td>
<td>설정 하나로 지연 로딩 시 <code>IN (?, ?, ...)</code> 쿼리로 묶어서 처리</td>
<td>쿼리가 1개로 줄어드는 것은 아니며 <code>1 + (N/size)</code>회 실행됨</td>
</tr>
</tbody></table>

<h2>6. 컬렉션 페치 조인과 페이징(Pagination)의 한계와 해법</h2>
<h3>문제: 1:N 컬렉션 페치 조인 시 페이징 쿼리가 실패하는 이유</h3>
<pre><code class="hljs language-java"><span class="hljs-comment">// [심각한 성능 장애 유발 코드]</span>
<span class="hljs-meta">@Query(&quot;select o from Order o join fetch o.orderItems&quot;)</span>
<span class="hljs-type">Page</span>&lt;Order&gt; <span class="hljs-title function_">findAllWithItems</span><span class="hljs-params">(Pageable pageable)</span>;</code></pre>
<ol>
<li>데이터베이스 관점에서 1:N 조인을 실행하면 부모 데이터(<code>Order</code>)가 자식 데이터(<code>OrderItem</code>) 개수만큼 <strong>중복으로 뻥튀기(Row 확장)</strong> 된다.</li>
<li>이 상태에서 DB의 <code>LIMIT / OFFSET</code> 페이징을 적용하면 1번 주문의 데이터가 잘려 나가는 등 데이터 왜곡이 발생한다.</li>
<li>Hibernate는 데이터 정합성을 지키기 위해 <strong>DB 레벨 페이징을 포기하고, DB의 모든 데이터를 애플리케이션 메모리로 퍼올린 뒤 메모리에서 직접 페이징(In-Memory Paging)</strong> 을 수행한다.</li>
<li>로그에 <code>HHH000104: firstResult/maxResults specified with collection fetch; applying in-memory!</code> 경고가 찍히며, 데이터가 많을 경우 즉시 <strong>OutOfMemoryError(OOM)</strong> 가 발생하여 서버가 다운된다.</li>
</ol>
<h3>실무 표준 해결 공식 (2단계 접근법)</h3>
<pre><code class="hljs">[<span class="hljs-number">1</span>단계]: <span class="hljs-title class_">ToOne</span> 관계(<span class="hljs-title class_">Member</span>, <span class="hljs-title class_">Delivery</span>)만 페치 조인하여 DB 레벨 페이징 수행
         ▼
[<span class="hljs-number">2</span>단계]: <span class="hljs-title class_">ToMany</span> 컬렉션(<span class="hljs-title class_">OrderItems</span>)은 default_batch_fetch_size를 통해 IN 쿼리로 최적화 조회</code></pre>
<h4>Step 1. ToOne 관계만 페치 조인하여 페이징 조회</h4>
<pre><code class="hljs language-java"><span class="hljs-keyword">public</span> <span class="hljs-keyword">interface</span> <span class="hljs-title class_">OrderRepository</span> <span class="hljs-keyword">extends</span> <span class="hljs-title class_">JpaRepository</span>&lt;Order, Long&gt; {

    <span class="hljs-meta">@Query(value = &quot;select o from Order o join fetch o.member m join fetch o.delivery d&quot;,
           countQuery = &quot;select count(o) from Order o&quot;)</span>
    <span class="hljs-type">Page</span>&lt;Order&gt; <span class="hljs-title function_">findAllOrdersWithPaging</span><span class="hljs-params">(Pageable pageable)</span>;
}</code></pre>
<p><code>ToOne</code> 관계는 조인해도 데이터 Row 수가 늘어나지 않으므로 DB <code>LIMIT / OFFSET</code> 페이징이 정상 동작한다.</p>
<h4>Step 2. <code>application.yml</code>에 BatchSize 전역 설정</h4>
<pre><code class="hljs language-yaml"><span class="hljs-attr">spring:</span>
  <span class="hljs-attr">jpa:</span>
    <span class="hljs-attr">properties:</span>
      <span class="hljs-attr">hibernate:</span>
        <span class="hljs-attr">default_batch_fetch_size:</span> <span class="hljs-number">100</span> <span class="hljs-comment"># 보통 100~500 권장</span></code></pre>
<h4>Step 3. DTO 변환 시 지연 로딩 호출</h4>
<pre><code class="hljs language-java"><span class="hljs-meta">@Transactional(readOnly = true)</span>
<span class="hljs-keyword">public</span> <span class="hljs-type">Page</span>&lt;OrderResponse&gt; <span class="hljs-title function_">getOrders</span><span class="hljs-params">(Pageable pageable)</span> {
    <span class="hljs-type">Page</span>&lt;Order&gt; <span class="hljs-variable">orderPage</span> <span class="hljs-operator">=</span> orderRepository.findAllOrdersWithPaging(pageable);

    <span class="hljs-comment">// order.getOrderItems() 호출 시 100개 단위의 IN (?, ?, ...) 쿼리 1회로 최적화되어 조회됨</span>
    <span class="hljs-keyword">return</span> orderPage.map(OrderResponse::from);
}</code></pre>

<h2>7. 동시성 제어: 낙관적 락 vs 비관적 락</h2>
<p>동시에 여러 트랜잭션이 동일한 엔티티를 수정하려 할 때 데이터 정합성을 보장하는 방법이다.</p>
<h3>1) 낙관적 락 (Optimistic Lock)</h3>
<ul>
<li><strong>개념</strong>: &quot;데이터 충돌이 대부분 발생하지 않을 것이다&quot;라고 가정하고 DB 락 대신 애플리케이션 레벨에서 버전 관리로 충돌을 감지한다.</li>
<li><strong>적용</strong>: 엔티티에 <code>@Version</code> 필드를 추가한다.</li>
</ul>
<pre><code class="hljs language-java"><span class="hljs-meta">@Entity</span>
<span class="hljs-keyword">public</span> <span class="hljs-keyword">class</span> <span class="hljs-title class_">Article</span> {
    <span class="hljs-meta">@Id</span> <span class="hljs-meta">@GeneratedValue</span>
    <span class="hljs-keyword">private</span> Long id;

    <span class="hljs-keyword">private</span> String title;

    <span class="hljs-meta">@Version</span>
    <span class="hljs-keyword">private</span> Long version; <span class="hljs-comment">// 수정 시마다 Hibernate가 자동으로 1씩 증가시킴</span>
}</code></pre>
<pre><code class="hljs language-sql"><span class="hljs-comment">-- 내부 실행 쿼리</span>
<span class="hljs-keyword">UPDATE</span> article 
<span class="hljs-keyword">SET</span> title <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;수정된 제목&#x27;</span>, version <span class="hljs-operator">=</span> <span class="hljs-number">2</span> 
<span class="hljs-keyword">WHERE</span> id <span class="hljs-operator">=</span> <span class="hljs-number">1</span> <span class="hljs-keyword">AND</span> version <span class="hljs-operator">=</span> <span class="hljs-number">1</span>;</code></pre>
<p>동시에 다른 트랜잭션이 먼저 수정하여 버전이 2로 올라갔다면, 조건에 맞는 레코드가 없어 업데이트 수가 0이 되고 <code>ObjectOptimisticLockingFailureException</code>이 발생한다.</p>
<ul>
<li><strong>장점</strong>: 별도의 DB 락을 잡지 않으므로 처리량(Throughput)이 높다.</li>
<li><strong>단점</strong>: 충돌 발생 시 롤백 및 재시도(Retry) 로직을 개발자가 직접 작성해야 한다.</li>
<li><strong>추천</strong>: 게시글 수정, 상품 설명 수정 등 동시 수정 충돌 가능성이 낮은 경우.</li>
</ul>
<h3>2) 비관적 락 (Pessimistic Lock)</h3>
<ul>
<li><strong>개념</strong>: &quot;데이터 충돌이 반드시 일어날 것이다&quot;라고 가정하고, 조회 시점에 DB의 배타적 락(<code>SELECT ... FOR UPDATE</code>)을 걸어 다른 트랜잭션의 접근을 대기시킨다.</li>
</ul>
<pre><code class="hljs language-java"><span class="hljs-keyword">public</span> <span class="hljs-keyword">interface</span> <span class="hljs-title class_">ProductRepository</span> <span class="hljs-keyword">extends</span> <span class="hljs-title class_">JpaRepository</span>&lt;Product, Long&gt; {

    <span class="hljs-meta">@Lock(LockModeType.PESSIMISTIC_WRITE)</span>
    <span class="hljs-meta">@Query(&quot;select p from Product p where p.id = :id&quot;)</span>
    <span class="hljs-type">Optional</span>&lt;Product&gt; <span class="hljs-title function_">findByIdWithPessimisticLock</span><span class="hljs-params">(<span class="hljs-meta">@Param(&quot;id&quot;)</span> Long id)</span>;
}</code></pre>
<ul>
<li><strong>장점</strong>: 트랜잭션이 끝날 때까지 다른 트랜잭션이 대기하므로 데이터 무결성이 완벽히 보장된다.</li>
<li><strong>단점</strong>: 대기 시간으로 인해 동시 처리 성능이 떨어지고 데드락(Deadlock) 위험이 증가한다.</li>
<li><strong>추천</strong>: 한정 수량 재고 차감, 포인트/계좌 출금 등 데이터 정합성이 최우선인 금융/결제 도메인.</li>
</ul>

<h2>8. OSIV (Open Session In View) 아키텍처 전략</h2>
<p><code>spring.jpa.open-in-view</code> 설정은 애플리케이션의 커넥션 관리와 직결되는 매우 중요한 옵션이다.</p>
<pre><code class="hljs language-yaml"><span class="hljs-attr">spring:</span>
  <span class="hljs-attr">jpa:</span>
    <span class="hljs-attr">open-in-view:</span> <span class="hljs-literal">false</span> <span class="hljs-comment"># 실무 API 서버 필수 권장</span></code></pre>
<h3>OSIV 동작 비교</h3>
<table>
<thead>
<tr>
<th>구분</th>
<th>OSIV ON (<code>true</code>, 기본값)</th>
<th>OSIV OFF (<code>false</code>, 권장)</th>
</tr>
</thead>
<tbody><tr>
<td><strong>커넥션 유지 범위</strong></td>
<td>HTTP 요청 시작 $\rightarrow$ 응답 반환 끝까지</td>
<td><code>@Transactional</code> 서비스 메서드 실행 구간만</td>

<td>Controller, View 템플릿 어디서나 가능</td>
<td><strong><code>@Transactional</code> 트랜잭션 내부에서만 가능</strong></td>

<tr>
<td><strong>장점</strong></td>
<td>DTO 변환 시 지연 로딩이 자유로워 개발 편의성 높음</td>
<td>DB 커넥션을 필요한 순간에만 쓰고 즉시 반납하므로 커넥션 풀 고갈 방지</td>
</tr>
<tr>
<td><strong>단점 및 위험</strong></td>
<td>외부 API 호출이나 무거운 작업 지연 시 DB 커넥션 풀이 마르는 장애 발생</td>
<td>트랜잭션 밖에서 지연 로딩 접근 시 <code>LazyInitializationException</code> 발생</td>
</tr>
</tbody></table>
<h3>OSIV OFF 환경에서의 아키텍처 패턴 (CQRS 쿼리 서비스 분리)</h3>
<p><code>open-in-view: false</code>를 적용하면 트랜잭션 밖에서는 지연 로딩을 쓸 수 없다. 이를 위해 복잡한 화면/API 조회의 경우 <strong>조회 전용 서비스(QueryService)</strong> 를 분리하여 트랜잭션 안에서 DTO로 완벽히 변환하여 반환하도록 설계한다.</p>
<pre><code class="hljs language-java"><span class="hljs-comment">// [조회 전용 서비스]</span>
<span class="hljs-meta">@Service</span>
<span class="hljs-meta">@RequiredArgsConstructor</span>
<span class="hljs-meta">@Transactional(readOnly = true)</span> <span class="hljs-comment">// 읽기 전용 트랜잭션 안에서 안전하게 DTO 변환</span>
<span class="hljs-keyword">public</span> <span class="hljs-keyword">class</span> <span class="hljs-title class_">OrderQueryService</span> {

    <span class="hljs-keyword">private</span> <span class="hljs-keyword">final</span> OrderRepository orderRepository;

    <span class="hljs-keyword">public</span> <span class="hljs-type">List</span>&lt;OrderDto&gt; <span class="hljs-title function_">getOrderDtos</span><span class="hljs-params">(Pageable pageable)</span> {
        <span class="hljs-keyword">return</span> orderRepository.findAllOrdersWithPaging(pageable)
                .map(OrderDto::from) <span class="hljs-comment">// 트랜잭션 내부이므로 지연 로딩 호출 가능</span>
                .toList();
    }
}</code></pre>
